# TSK-01-06 결과 — 가상 결과 그리드 100만 행 시험 (T-D02)

측정일 2026-10-19 · 레인 l0106-grid · 원자료 `results/*.txt` · 재실행 `run-measure.ps1`

## 요약

- 직접 그리기 가상 그리드(`Control.Render`, 셀 컨트롤 0개)는 100만 행 × 50열에서 **UI 스레드 비용이 프레임당 평균 0.9~6.1 ms(p95 1.1~17 ms)** 이다. 텍스트 캐시를 GlyphRun 으로 만들었을 때의 값이다.
- **60 fps 는 이 환경에서 확인하지 못했다.** 원격 데스크톱(RDP) 세션이라 GPU(ANGLE) 창의 프레임 간격이 원격 디스플레이 주기 32 Hz(31.25 ms)에 묶였다. 이 상한 안에서는 4개 시나리오 모두 31.6~31.9 fps 로 상한에 붙었다(V-smooth 만 28.6). 소프트웨어 렌더 창은 32 Hz 에 묶이지 않았고 37~42 fps 였다.
- 페이지 캐시: 50열 혼합 결과에서 **행당 약 1.0 KB**(관리 힙). 500행 페이지 1개 ≈ 490 KB, 200 MB 상한 ≈ 400페이지 ≈ 20만 행.
- **TRD 4.4 에 적힌 "셀 단위 FormattedText 캐시"는 쓰면 안 된다.** Avalonia 12 의 `FormattedText` 는 그릴 때마다 줄을 다시 포맷한다. 그래서 캐시해도 그리기 비용이 줄지 않는다. 셀 텍스트는 **GlyphRun 캐시**(ASCII 빠른 경로, 그 밖의 문자는 TextLayout)로 바꿔야 한다.
- TreeDataGrid.Avalonia 12.0.0(MIT 포크)과 비교했다. 같은 시나리오에서 2.6~22 fps 였다. 빠른 스크롤·점프에서는 직접 그리기 그리드보다 약 8배 느렸다.

## 환경과 측정 방법

| 항목 | 값 |
|---|---|
| 기기 | Intel i5-1135G7 (4C/8T) 노트북, 32 GB, Intel Iris Xe |
| OS / 세션 | Windows 11 Pro 10.0.26300, **RDP 세션(RDP-Tcp#0)**. 원격 디스플레이 어댑터 32 Hz, 로컬 패널 60 Hz |
| 런타임 | .NET 10.0.13, Avalonia 12.1.4(Skia), Release, Workstation GC |
| 창 / 그리드 | 1600×900, 배율 1.0. 행 22 px, 화면당 약 40행 × 12~14열 = 492~574셀 |
| 데이터 | 합성 1,000,000행 × 50열(NUMBER·VARCHAR2 8~40자·DATE·NUMBER(10,2)·코드), 페이지 500행, 열 지향 버퍼, LRU 400페이지 |
| 측정 잠금 | 잡고 측정함(2회). 다른 레인 프로세스 때문에 CPU 부하가 44%(1차)·80%(TDG 회차)였다. **숫자에 잡음이 있다** |

시나리오는 각 10초이고, 앞에 2초 예열을 둔다.
- **V-smooth**: 3행(66 px)/프레임
- **V-fast**: 60행/프레임. 스크롤바를 빠르게 끄는 경우이며, 프레임마다 모든 셀이 새 텍스트다
- **H-scroll**: 40 px/프레임 왕복, 50만 번째 행 근처
- **Jump**: 프레임마다 무작위 행·열로 이동. 거의 매 프레임 페이지를 새로 가져오고 모든 셀이 새 텍스트다

측정 모드는 셋이다.
- **window**: 실제 창이다. `TopLevel.RequestAnimationFrame` 콜백 간격을 프레임 시간으로 보고, `Render()` 안의 시간(UI 스레드에서 그리기 명령을 기록하는 시간)을 따로 잰다. 렌더 스레드의 합성·래스터 시간은 따로 재지 못했다. 다만 프레임 간격에는 반영된다.
- **offscreen**: `RenderTargetBitmap` 이다. CPU Skia 로 그리기 명령 기록과 래스터를 합친 시간을 vsync 없이 잰다. 헤드리스에 가장 가까운 상한이고, GPU 는 쓰지 않는다.
- **mem**: GC 를 3번 돌려 안정시킨 뒤 관리 힙 증가량을 잰다. 프로세스 private bytes 증가량도 함께 적는다.

텍스트 캐시 방식은 셋이다. 캐시는 2세대(이번 프레임/직전 프레임)이며 화면에 보이는 셀만 남긴다.
- `formatted` = `FormattedText`
- `layout` = `TextLayout`
- `glyph` = 글리프 번호와 advance 표로 shaping 없이 `GlyphRun` 을 만든다. ASCII 가 아닌 문자는 TextLayout 으로 넘긴다.

## 해석

1. **UI 스레드는 60 fps 예산(16.7 ms) 안에 들어온다.** glyph 방식의 `Render()` 는 평균 0.6~6 ms 이다. 최악 시나리오인 Jump 도 p95 17 ms 로 예산 경계에 있다. 이 값은 페이지를 동기로 가져오는 시간 약 2 ms 를 포함한다. 실제 제품은 페이지를 비동기로 가져오므로 그보다 작아진다.
2. **60 fps 여부를 가르는 것은 렌더 스레드의 래스터다.** CPU 래스터만으로 재면 평균 10~25 ms 로 60 fps 에 못 미친다. GPU(ANGLE) 창에서는 RDP 때문에 32 Hz 를 넘는 값을 볼 수 없었다. 32 Hz 상한에서 GPU 창은 V-fast·H-scroll·Jump 에서 프레임을 거의 떨어뜨리지 않았다(p95 ≈ 33 ms ≈ 1주기). 그래서 GPU 경로라면 여유가 있을 것으로 **추정**하지만, 확인하지는 못했다.
3. **FormattedText 캐시는 효과가 없다.** 캐시해도 그리기 비용이 25~30 ms 나 들었다. TextLayout 은 그리기 비용은 낮췄지만 생성이 비싸다(셀당 52~144 µs × 500셀 ≈ 20 ms). GlyphRun 은 생성과 그리기가 모두 싸다.
4. **TreeDataGrid 포크는 대안이 될 수 없다.** 행·셀이 컨트롤이라 빠른 스크롤에서 프레임당 250~380 ms 가 걸린다. 100만 행 범위 자체는 처리한다(extent 25,000,000 px).

## 한계

- RDP 세션이다. GPU 창은 32 Hz 에 묶였고, 로컬 콘솔(60 Hz 패널)에서 다시 재지 못했다.
- 렌더 스레드(합성·래스터)의 시간을 따로 재지 못했다. 프레임 간격과 오프스크린 CPU 래스터로 간접 추정했다.
- 측정 중 다른 레인 프로세스(dotnet 십여 개) 때문에 CPU 부하가 44~80% 였다. 숫자는 보수적인(나쁜 쪽) 값으로 본다.
- glyph 빠른 경로는 ASCII 만 처리하고, 커닝·합자를 적용하지 않는다. 한글·CJK 셀의 비용과 폰트 대체는 측정하지 않았다(TextLayout 으로 넘김). HiDPI(배율 1.25~2.5)도 측정하지 않았다.
- 데이터 생성(가짜 fetch)이 Render 안에서 동기로 돈다. Jump 의 2~3 ms 가 여기서 나온다.
- 선택·편집·열 크기 조절·접근성은 이 시제품의 범위 밖이다.

## T-D02 결정 후보

1. **결과 그리드는 직접 그리기 가상 그리드로 확정한다.** UI 스레드 비용은 프레임당 6 ms 이하(p95 17 ms 이하)였다. TreeDataGrid.Avalonia 12.0.0(MIT 포크)은 같은 시나리오에서 2.6~22 fps 라서 대안에서 뺀다.
2. **셀 텍스트 캐시는 FormattedText 가 아니라 GlyphRun 으로 한다.** ASCII 는 글리프 표를 써서 shaping 없이 GlyphRun 을 만들고, 그 밖의 문자는 TextLayout 으로 넘긴다. TRD 4.4 의 "FormattedText 캐시" 문구를 고쳐야 한다. 페이지 캐시 기준은 50열 혼합에서 행당 약 1 KB 이고, 200 MB 상한 ≈ 20만 행이다.
3. **60 fps 는 아직 미확인이다.** 로컬 콘솔(비 RDP, 60 Hz 이상, GPU)에서 `run-measure.ps1` 을 다시 돌려 확정한다. M2 의 성능 테스트(TRD 8장)에서 같은 시나리오를 다시 쓴다.
