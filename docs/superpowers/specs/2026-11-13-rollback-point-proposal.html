커밋한 뒤에도 실행 직전으로 되돌리기

쓰기 문장을 실행할 때 그 문장을 거꾸로 되돌리는 원복 스크립트를 함께 만들어 둡니다. UPDATE 는 이전 값으로 되돌리는 UPDATE, DELETE 는 지운 행을 넣는 INSERT, INSERT 는 넣은 행을 지우는 DELETE 가 됩니다. 원복 스크립트가 없는 실행은 실행 직전 SCN 을 기준으로 지금과 비교해 되돌립니다.

작성 2026-11-12 상태 사용자 확인 전 (구현 안 함) 관련 TSK-13-05 플래시백 · TSK-13-07 변경 일지 · SAFE-03

2판에서 바뀐 것 원복 스크립트를 중심 방식으로 올렸습니다. 안전장치 네 가지(먼저 잠그기, 실행 직후 값 조건, 커밋 단위 역순 파일, 암호화 보관)와, 적용하면서 찾은 보완 세 가지를 반영했습니다. 원복 스크립트 화면을 새로 그렸고, 확인 창·설정·비교표·정하실 것·단계안을 맞춰 고쳤습니다.
3판에서 정한 것 원복 스크립트는 운영 접속에서만 만듭니다. 개발·테스트 접속은 SCN 만 기록하고 시점 비교(화면 3)로 되돌립니다.

지금 되는 것과 비어 있는 곳

실수가 일어나는 곳을 기준으로 나누면, 그리드 편집과 DDL 은 일부 대비되어 있고 SQL 편집기에서 실행한 DML 은 대비가 전혀 없습니다.

실수한 곳대비 정도지금 되는 것빠진 것
SQL 편집기
UPDATE·DELETE·INSERT 실행 후 커밋		 없음 없음 어느 시점으로 돌아가야 하는지조차 기록되지 않습니다. 사용자가 시각을 추측해 직접 AS OF 질의를 써야 합니다.
결과 그리드 편집
반영 후 커밋		 일부 플래시백 메뉴: N분 전 값 보기, 이 행 변경 이력, 이전 값으로 되돌리기(UPDATE 미리보기 후 반영) 그리드에 남은 행만 되돌립니다. 지운 행은 그리드에 없어서 되살리지 못하고, 새로 넣은 행은 건너뜁니다. 기준 시점은 「N분 전」뿐입니다.
DDL·PL/SQL 컴파일
ALTER·DROP·CREATE OR REPLACE·RENAME		 일부 변경 일지가 실행 직전의 DDL 을 앱 안에 자동으로 보관합니다. 보관본을 새 편집기에 열어 직접 실행합니다. TRUNCATE 는 보관하지 않습니다. 구조만 보관하므로 DROP COLUMN·TRUNCATE 로 사라진 데이터는 살리지 못합니다. DDL 뒤에는 AS OF 질의가 ORA-01466 으로 막힙니다.

A · 중심 방식

원복 스크립트

  • 문장마다 거꾸로 되돌리는 SQL 을 만들어 커밋 한 번 단위의 파일로 보관합니다.
  • undo 보존 기간, FLASHBACK 권한과 상관없이 씁니다.
  • 사람이 읽고 고칠 수 있는 SQL 입니다.
  • 운영 접속에서만 만듭니다.
B · 항상 켬

실행 지점 기록

  • 쓰기 문장을 보내기 직전에 SCN 숫자 하나를 변경 일지에 남깁니다.
  • 원복 스크립트를 만들지 않은 실행도 이 시점으로 비교해 되돌릴 수 있습니다.
C · B 를 쓸 때

시점 비교 되돌리기

  • 기록한 SCN 시점과 지금 데이터를 키로 견주어 보상 DML 을 만듭니다.
  • undo 보존 기간 안에서만 됩니다.
  • SCN 이 없으면 시각을 직접 고릅니다.
원복 스크립트

문장 하나를 실행할 때 일어나는 순서

UPDATE 를 예로 들었습니다. 사용자가 보는 화면에는 변화가 없고, 실행 로그에 「원복 스크립트 12문장」 한 줄이 더해질 뿐입니다.

1 · 먼저 잠그고 읽기 
SELECT ROWID, PRODUCT_ID, UNIT_PRICE
  FROM SAMPLE.PRODUCTS
 WHERE CATEGORY_ID = 3
   FOR UPDATE

사용자 문장과 같은 WHERE 로 이전 값을 읽으면서 행을 잠급니다. 키 열과 SET 대상 열만 읽습니다.

2 · 사용자 문장 실행 
UPDATE SAMPLE.PRODUCTS
   SET UNIT_PRICE = UNIT_PRICE * 1.1
 WHERE CATEGORY_ID = 3

영향 행 수(12)가 잠근 행 수(12)와 같은지 바로 견줍니다.

3 · 실행 직후 값 읽기 
SELECT ROWID, UNIT_PRICE
  FROM SAMPLE.PRODUCTS
 WHERE ROWID IN (…잠근 행…)

아직 커밋 전이라 내 세션의 바뀐 값이 보입니다. 이 값을 원복 문장의 조건에 넣습니다.

4 · 커밋 또는 롤백 
COMMIT    → 파일 확정
ROLLBACK  → 파일 무효
ROLLBACK TO 저장점
          → 그 뒤 문장만 무효

트랜잭션의 끝을 Oranda 가 알고 있으므로 파일의 상태를 함께 바꿉니다.

실행한 문장원복 문장먼저 읽는 것원복 문장의 조건
UPDATE이전 값으로 되돌리는 UPDATEROWID, 키 열, SET 대상 열키 = 값 그리고 SET 대상 열 = 실행 직후 값
DELETE지운 행을 넣는 INSERT모든 열조건 없음. 같은 키가 이미 있으면 ORA-00001 이 나며, 이것을 충돌로 알립니다.
INSERT … VALUES넣은 행을 지우는 DELETE없음. 실행 뒤 RETURNING ROWID 로 넣은 행을 찾아 읽습니다.키 = 값 그리고 모든 열 = 넣은 값
INSERT … SELECT넣은 행을 지우는 DELETESELECT 목록에 키 열이 그대로 있으면 그 SELECT 를 먼저 실행해 키를 얻습니다.키를 얻지 못하면(시퀀스·트리거·식) 원복 스크립트를 「불완전」으로 표시합니다.

적용한 안전장치

앞 대화에서 제안한 네 가지를 채운 색으로, 적용하면서 새로 찾은 보완 세 가지를 점선으로 표시했습니다.

1먼저 잠그고 읽기

같은 WHERE 로 SELECT … FOR UPDATE 를 먼저 실행합니다. 읽은 뒤 실행하기 전에 다른 세션이 값을 바꾸어 원복 값이 어긋나는 일을 막습니다.

2실행 직후 값을 조건에 넣기

원복 UPDATE·DELETE 는 「실행 직후 값과 지금 값이 같은 행」만 바꿉니다. 그 뒤 다른 사람이 다시 바꾼 행은 0행으로 끝나므로 덮어쓰지 않습니다.

3커밋 단위 파일, 역순, 롤백하면 무효

커밋 한 번이 파일 하나입니다. 원복 문장은 실행한 문장의 역순으로 써서, 지운 부모 행이 자식 행보다 먼저 되살아나게 합니다.

4암호화 보관과 상한

파일에는 실제 데이터가 들어가므로 접속 비밀번호와 같은 OS 보안 저장소의 키로 암호화합니다. 문장당 행 수 상한과 보관 기간을 둡니다.

+행 수 대조

잠근 행 수와 실제 영향 행 수가 다르면(WHERE 에 SYSDATE·ROWNUM 이 있거나, 그 사이 다른 세션이 조건에 맞는 행을 넣은 경우) 커밋하기 전에 경고하고 스크립트를 「불완전」으로 표시합니다.

+키를 먼저 쓰고 ROWID 는 보조

지웠다가 되살린 행은 ROWID 가 바뀝니다. 그래서 원복 문장은 PK 로 행을 찾고, PK 가 없는 테이블이나 PK 를 바꾼 UPDATE 에서만 ROWID 를 씁니다.

+NULL 은 IS NULL

조건에 넣는 값이 NULL 이면 = NULL 이 아니라 IS NULL 로 씁니다. 날짜·RAW 같은 값은 지금 플래시백과 「INSERT 문으로 복사」가 쓰는 리터럴 규칙을 그대로 씁니다.

한계로 받아들이는 것

  • 실행 시간: 원복 스크립트를 만들면 같은 조건으로 한 번 더 읽고 잠그므로, 대량 DML 은 시간이 두 배 가까이 걸릴 수 있습니다. 그래서 상한을 두고, 운영 접속에서만 만듭니다.
  • 키를 알 수 없는 INSERT: INSERT … SELECT 에서 키가 시퀀스·트리거·식으로 정해지면 넣은 행을 찾지 못합니다. 이때는 스크립트를 「불완전」으로 두고, 시점 비교(화면 3)로 넘깁니다.
  • 대상이 아닌 문장: MERGE, PL/SQL 블록 안의 DML, 뷰를 통한 DML, DB 링크 너머의 테이블은 처음 단계에서 원복 스크립트를 만들지 않고 SCN 만 기록합니다.
  • 트리거·ON DELETE CASCADE로 다른 테이블이 함께 바뀐 것은 원복 스크립트에 들어가지 않습니다. 대상 테이블에 트리거나 CASCADE FK 가 있으면 확인 창에서 미리 알립니다.
  • LOB·LONG 같은 큰 열은 문자 리터럴 한도(4000바이트) 때문에 SQL 로 쓰기 어렵습니다. 처음 단계에서는 이런 열이 있는 행을 「불완전」으로 표시합니다.
  • 문장 하나만 되돌리기는 원복 스크립트에서 그 묶음만 골라 실행하는 방식으로 합니다. 시점 비교는 커밋 단위로만 됩니다.

정하실 것

아래 항목은 답에 따라 만드는 범위가 달라집니다. 각 항목의 제안은 제 판단입니다.

1. 원복 스크립트를 어느 접속에서 만들지 정함

운영 접속에서만 만듭니다(2026-11-12 사용자 결정). 개발·테스트 접속은 SCN 만 기록하고, 되돌릴 때는 시점 비교(화면 3)를 씁니다.

2. 키를 알 수 없는 INSERT 처리

한 행 INSERT … VALUES 는 Oranda 가 문장 끝에 RETURNING ROWID INTO 를 붙여 실행하면 넣은 행을 찾을 수 있습니다. 다만 사용자가 쓴 문장을 바꿔서 보내는 셈입니다.

제안 한 행 VALUES 는 RETURNING 을 붙이고 실행 로그에 그 사실을 남깁니다. INSERT … SELECT 는 불완전으로 둡니다.

3. FLASHBACK TABLE 을 다시 범위에 넣을지

TSK-13-05 에서 범위 밖으로 정했습니다. 빠르지만 다른 사람의 변경까지 지우고, ROW MOVEMENT 를 켜는 DDL 이 필요합니다.

제안 넣지 않습니다. 원복 스크립트와 시점 비교가 미리보기와 함께 같은 결과를 냅니다.

4. 그리드의 「이전 값으로 되돌리기」와 합칠지

지금은 「N분 전」만 고를 수 있고 지운 행을 되살리지 못합니다. 그리드 반영도 DML 이므로 운영 접속에서는 원복 스크립트가 함께 만들어집니다.

제안 그리드 명령도 화면 3 의 비교를 쓰게 바꾸고, 시점 목록에 일지의 커밋 묶음을 넣습니다.
