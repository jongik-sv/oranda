# 접속 간 데이터 복사 설계

작성일: 2026-11-06. 상태: 구현됨(2026-11-06, 계획 `docs/superpowers/plans/2026-11-06-cross-connection-data-copy.md` T1~T12). 시안은 사용자가 확인했다(2026-11-06). PRD 번호: EXP-04. 구현 결정과 설계에서 달라진 점은 13장에 적었다.

표기: **[사용자]** = 사용자가 결정함, **[설계]** = 작성자가 정함(사용자가 뒤집을 수 있음), **[구현]** = 구현자에게 맡김.

시안(화면 3장): https://claude.ai/artifact/AkF7RS4monhDx8vWWX1TqN — 1 규칙 편집, 2 사전 점검, 3 실행·검증.

## 1. 의도

사용자 팀은 운영계 데이터 일부(예: 최근 1달)를 테스트계로 옮겨 테스트 데이터로 쓴다. 정책상 운영계 → 테스트계 이관은 허용되어 있다 **[사용자]**.

그러나 이 팀의 환경에서는 서버 쪽 방법을 쓸 수 없다 **[사용자]**.

- Data Pump: 서버 DIRECTORY 와 덤프 파일 이동이 필요하다.
- DB Link: 테스트 DB 서버에서 운영 DB 서버로 직접 접속할 수 있어야 한다.

두 방법 모두 DBA 협조가 필요한데, 협조를 기대하기 어렵다. 반면 사용자 PC 는 두 DB 에 모두 접속할 수 있다. 그래서 Oranda 가 원본 접속에서 읽은 행을 대상 접속에 배치로 넣는 **클라이언트 경유 복사**를 만든다 **[사용자]**. 이 기능은 `docs/idea.md` 의 「접속 간 데이터 복사」 항목을 구체화한 것이다.

필요한 테이블은 사람마다 다르다. 그래서 복사 작업(테이블 목록과 규칙)을 각자 PC 에 저장하고, 매달 다시 열어 실행한다 **[사용자]**.

## 2. 목표

- 원본 접속과 대상 접속을 고르고, 테이블마다 추출 규칙과 대상 처리를 정해 한 번에 복사한다.
- 부모 테이블과 자식 테이블을 같은 시점 기준으로 읽어 참조 무결성을 지킨다.
- 실행하기 전에 문제(권한, 열 차이, 트리거, 시퀀스, FK)를 사전 점검으로 보여 주고, 대상에서 실행할 SQL 을 미리 보여 준다.
- 같은 작업을 다시 실행해도 결과가 같다(기본 대상 처리가 「같은 범위 지우고 넣기」).
- 실행 중 진행률을 보여 주고, 끝나면 테이블마다 원본 건수와 대상 건수를 비교한다. 실패한 행은 원인과 함께 보여 준다.
- 복사 작업을 사용자 PC 에 저장하고, 내보내기·가져오기로 동료와 주고받는다 **[사용자]**.
- DBA 권한이나 추가 권한 없이 동작한다. 원본은 테이블 SELECT, 대상은 테이블 INSERT·UPDATE·DELETE(와 조회용 SELECT) 권한만 있으면 모든 기본 동작이 되어야 한다 **[사용자]**. 대상 접속 계정은 테이블 소유자가 아닐 수 있다.

## 3. 비목표

- Data Pump, DB Link, SQL\*Loader 연동.
- 개발 접속이 아닌 대상에 테이블 만들기(DDL). 테스트 접속에서는 대상 테이블이 이미 있어야 하고, 구조 차이는 사전 점검에서 알려 주기만 한다. 개발 접속은 6.2.3 의 「테이블 다시 만들기」를 쓸 수 있다.
- Oracle 이외 DBMS.
- 예약 실행·자동 반복. 사용자가 직접 연다.
- 앱이 죽은 뒤 중간부터 이어서 실행하기. 다시 실행하면 같은 결과가 나오므로 처음부터 다시 실행한다 **[설계]**.
- 팀 공용 서버 저장소. 공유는 작업 파일 내보내기·가져오기로만 한다 **[사용자]**.
- 행 단위 차이 비교·동기화(`docs/idea.md` 「데이터 비교·동기화」는 별개 기능).

## 4. 실패로 보는 경우

기능이 동작해도 다음 중 하나면 실패다.

- 운영(`ConnectionEnvironment.Production`) 접속에 쓰기가 일어난다. 대상으로 운영 접속을 고를 수 없어야 하고, 우회 설정도 두지 않는다 **[설계]**.
- 원본 세션에서 SELECT 외의 문장이 실행된다.
- 환경 라벨이 개발(`ConnectionEnvironment.Development`)이 아닌 대상에서 `DROP TABLE`·`CREATE TABLE` 이 실행된다.
- 쓰기 문장이 정책 관문(`IExecutionPolicy`)을 건너뛴다. 읽기 전용 프로필이나 조회 전용 Role 인 대상은 지금처럼 거부되어야 한다.
- 복사가 실패하거나 중지된 뒤 대상 트리거가 꺼진 채로 남았는데 사용자가 모른다.
- 사용자가 명시적으로 저장하지 않았는데 운영 데이터가 디스크(로그, 실행 기록, 임시 파일)에 남는다. 예외는 실패 행의 키 열 값 하나뿐이다(9장). 마스킹 대상 열 값은 어떤 경우에도 남기지 않는다.
- 작업 파일에 비밀번호가 들어간다.
- 실제 서버 주소나 회사 DB 별칭이 리포(코드·시험·문서·커밋)에 들어간다.

## 5. 사용자 흐름

1. 메뉴 「도구 › 데이터 복사…」로 창을 연다 **[설계]**. 스키마 브라우저에서 테이블을 오른쪽 클릭해 「데이터 복사에 추가」로 열 수도 있다 **[설계]**.
2. **규칙 편집**: 내 작업 목록에서 작업을 고르거나 새로 만든다. 원본·대상 접속, 기간, 테이블별 규칙을 정한다.
3. **사전 점검**: 점검 결과와 대상에서 실행할 SQL 을 확인한다. 확인이 필요한 항목은 선택지(예: 트리거 끄기)를 고른다.
4. **실행·검증**: 실행하고 진행 상황을 본다. 끝나면 건수 비교와 실패한 행을 확인한다.

창은 모달이 아닌 별도 창이다 **[설계]**. 실행하는 동안에도 Oranda 의 다른 작업을 할 수 있다.

## 6. 복사 작업 모델

### 6.1 작업(CopyJob)

| 필드 | 뜻 |
|---|---|
| `schemaVersion` | 파일 형식 버전 |
| `id`, `name` | 작업 식별자, 표시 이름 |
| `source`, `target` | 접속 참조(6.3) |
| `sourceOwner`, `targetOwner` | 원본·대상 테이블 소유자 스키마. 접속 계정과 다를 수 있다. 기본값은 서로 같은 이름 **[설계]** |
| `period` | 기간(6.4) |
| `tables[]` | 테이블 규칙 목록, 실행 순서대로 |
| `options` | 배치 크기(기본 5,000), 커밋 단위(기본 테이블마다), 트리거 끄기 기본값 |
| `sequences[]` | 시퀀스 보정 규칙(8.4) |
| `lastRun` | 마지막 실행 시각·결과·행 수(목록 표시용) |

### 6.2 테이블 규칙

| 규칙 | 원본에서 읽는 행 | 대상 처리 기본값 |
|---|---|---|
| 전체 | 모든 행 | PK 기준 MERGE(PK 가 없으면 비우고 넣기) |
| 기간 | 지정한 날짜 열이 `:FROM_DT` 이상, `:TO_DT` 미만 | 같은 범위 지우고 넣기 |
| 부모 키 | 부모 테이블 규칙이 읽은 행의 키에 연결된 행 | 같은 범위 지우고 넣기 |
| 직접 조건 | 사용자가 쓴 `WHERE` 조건(`:FROM_DT`·`:TO_DT` 사용 가능) | 같은 범위 지우고 넣기 |
| 제외 | 읽지 않음(목록에는 남김) | 없음 |

- 부모 키 규칙의 연결 열은 원본 테이블의 FK 에서 자동으로 찾는다(`ConstraintInfo.ReferencedTable`). FK 가 없는 업무 연결도 있으므로 사용자가 직접 지정할 수도 있다 **[설계]**.
- 부모 키 규칙은 여러 단계로 이어질 수 있다(손자 → 자식 → 부모). 생성하는 조건은 중첩 서브쿼리가 된다 **[설계]**.
- 기간의 경계는 시작 포함, 끝 제외(`>=`, `<`)로 고정한다 **[설계]**. 시안의 `BETWEEN` 표기는 이 뜻으로 바꾼다.
- 「전체」의 기본 대상 처리를 MERGE 로 둔 이유: 대상 계정은 FK 를 끌 권한이 없을 수 있다(2장). 기준정보 테이블은 거래 테이블이 FK 로 참조하는 경우가 많아서, 통째로 지우면 ORA-02292 로 실패한다. MERGE 는 원본에서 지워진 행을 대상에 남기는데, 이 점을 대상 처리 선택지 옆에 적어 둔다.

### 6.2.1 날짜 열 형식

날짜를 문자열로 저장한 열이 DATE 열보다 많다 **[사용자]**. 그래서 기간 규칙은 처음부터 두 종류를 모두 지원한다.

| 열 타입 | 비교 방법 |
|---|---|
| DATE, TIMESTAMP 계열 | 날짜 바인드와 비교: `열 >= :FROM_DT AND 열 < :TO_DT` |
| CHAR, VARCHAR2 | 기간을 지정한 형식의 문자열로 바꿔 바인드하고 문자열로 비교: `열 >= :FROM_S AND 열 < :TO_S` |

- 문자열 형식은 기간 규칙마다 고른다. 후보는 `YYYYMMDD`, `YYYYMMDDHH24MISS`, `YYYY-MM-DD`, `YYYY-MM-DD HH24:MI:SS`, `YYYYMM` 이고, 사용자가 직접 입력할 수도 있다 **[설계]**.
- 기본 형식은 열 길이로 추정한다: 6 → `YYYYMM`, 8 → `YYYYMMDD`, 10 → `YYYY-MM-DD`, 14 → `YYYYMMDDHH24MISS`, 19 → `YYYY-MM-DD HH24:MI:SS` **[설계]**.
- 열에 `TO_DATE` 를 씌우지 않는다. 씌우면 인덱스를 못 쓰고, 형식이 틀린 값 하나 때문에 조회 전체가 실패한다. 고정 길이에 0 을 채운 형식은 문자열 비교로 날짜 순서가 맞는다.
- `YYYYMM` 처럼 일 단위가 없는 형식은 기간 경계를 월 단위로 맞춘다(예: 「최근 1달」 → 지난달 `YYYYMM` 이상, 이번 달 이하). 정확한 규칙은 **[구현]**.
- 사전 점검은 기간 범위 안의 행 가운데 길이가 형식과 다른 값이 있는지 세어 보고, 있으면 확인 필요로 알린다 **[설계]**.
- 대상 쪽 범위 DELETE 와 부모 키 서브쿼리도 같은 비교 방법을 쓴다.

### 6.2.2 업무 날짜가 없는 테이블

업무 날짜 열이 없는 테이블은 감사(audit) 열의 생성 시각을 기간 기준으로 쓴다 **[사용자]**. 이 열은 TIMESTAMP 타입이다 **[사용자]**.

- 기간 규칙의 열 고르기 목록은 날짜·시각 타입 열과 길이가 맞는 문자열 열을 보여 준다. 업무 날짜로 보이는 열을 먼저 보이고, 그다음에 감사 열로 보이는 열(`CREATED_AT`, `CREATE_DT`, `CRT_DTM`, `REG_DTM`, `INS_DT`, `FRST_REG_DTM` 같은 이름)을 「생성 시각」 표시와 함께 보인다 **[설계]**. 이름 규칙 목록은 **[구현]**.
- 바인드 타입은 열 타입과 맞춘다 **[설계]**. DATE 열에는 DATE 바인드, TIMESTAMP 열에는 TIMESTAMP 바인드, TIMESTAMP WITH (LOCAL) TIME ZONE 열에는 그 타입의 바인드를 쓴다. 타입이 다르면 Oracle 이 열 쪽을 변환해서 인덱스를 못 쓰는 경우가 있다.
- 생성 시각 기준이면, 기간 전에 만들어졌지만 기간 안에 수정된 행은 복사되지 않는다. 이를 보완하려고 기간 규칙에 열을 두 개까지 지정해 OR 로 묶을 수 있게 한다(예: 생성 시각 또는 수정 시각) **[설계]**. 두 열의 형식은 각각 정한다.
- 대상 처리 4가지: 비우고 넣기, 같은 범위 지우고 넣기, 추가만, PK 기준 MERGE. 대상이 개발 접속이면 다섯 번째로 「테이블 다시 만들기」가 더해진다(6.2.3). 「비우고 넣기」는 `DELETE` 로 한다. `TRUNCATE` 는 FK 참조가 있으면 실패하고 되돌릴 수 없으므로 쓰지 않는다 **[설계]**.

### 6.2.3 테이블 다시 만들기 (개발 접속만)

대상 접속의 환경 라벨이 개발이면, 테이블을 지웠다가 원본 구조대로 새로 만든 뒤 넣는 대상 처리를 쓸 수 있다 **[사용자]**. 원본과 대상의 구조가 달라도 원본 구조로 맞출 수 있다는 장점이 있다. 테스트·운영 접속에서는 이 선택지가 보이지 않는다.

- **원본 구조 읽기**: 원본 계정은 테이블 소유자가 아닐 수 있다. 다른 스키마의 객체에 `DBMS_METADATA.GET_DDL` 을 쓰려면 SELECT_CATALOG_ROLE 이 필요하므로 쓰지 않는다. 대신 SELECT 권한만으로 읽을 수 있는 메타데이터(`TableInfo` 의 열, PK·UK·CHECK 제약, 인덱스, 주석)로 `CREATE TABLE` 문을 만든다 **[설계]**.
- **만들지 않는 것**: 테이블스페이스·저장 속성(대상 기본값을 쓴다), 파티션(일반 테이블로 만든다), 압축, 원본 트리거, 원본 권한 **[설계]**.
- **대상에 있던 것 보존**: 지우기 전에 대상 테이블에 걸려 있던 다음 항목의 DDL 을 받아 두었다가, 다시 만든 뒤 되살린다 **[설계]**. 트리거 본문은 `DBMS_METADATA.GET_DDL` 로 받고, 권한과 참조 FK 는 카탈로그로 문장을 만든다(13.2).
  - 트리거
  - 다른 계정에 준 권한(GRANT)
  - 다른 테이블이 이 테이블을 참조하던 FK
- **FK**: 작업 안에서 함께 다시 만드는 테이블끼리의 FK 는 원본 FK 대로 만들되, 적재가 끝난 뒤에 붙인다(13.2). 다른 테이블이 참조하던 FK 는 `DROP TABLE` 전에 먼저 떼어 내고(`ALTER TABLE ... DROP CONSTRAINT`), 받아 둔 DDL 로 적재가 끝난 뒤 되살린다. `CASCADE CONSTRAINTS` 는 붙이지 않는다(13.2). 되살릴 때 부모 없는 행이 있으면 `ENABLE NOVALIDATE` 로 켜고 결과에 보인다(8.2 의 FK 규칙과 같다).
- **휴지통**: `PURGE` 를 붙이지 않는다 **[설계]**. 지운 테이블이 휴지통(Recycle Bin)에 남아 `FLASHBACK TABLE ... TO BEFORE DROP` 으로 되돌릴 수 있다. Oranda 의 Flashback 화면에서 되돌리는 방법을 실행 결과에 안내한다.
- **정책**: `DROP TABLE` 은 정책 관문의 위험 명령이라 이름을 다시 입력해야 통과한다. 사전 점검에서 지울 테이블 목록을 한 번에 보여 주고, 사용자가 대상 접속 이름을 한 번 다시 입력하면 그 목록 전체에 대한 확인으로 본다 **[설계]**.
- **권한**: 대상 세션이 대상 소유자 계정이 아니거나, `CREATE TABLE`(대상 표에 트리거가 있으면 `CREATE TRIGGER` 도)이 없으면 사전 점검 오류다. `CREATE ANY TABLE`·`CREATE ANY TRIGGER` 는 인정한다. 설계 초안의 「그에 준하는 권한」은 소유자 세션으로 좁혔다(13.2).
- **적재**: 새로 만든 테이블은 비어 있으므로 범위 DELETE 와 PK MERGE 없이 바로 INSERT 한다.

### 6.3 접속 참조

접속 ID 는 PC 마다 다르다. 작업 파일에는 접속 **이름**과 사용자명을 저장하고, 접속 ID 는 같은 PC 에서 빨리 찾기 위한 힌트로만 둔다 **[사용자]**. 작업을 열 때 이 순서로 찾는다.

1. 같은 ID 이고 같은 이름인 접속.
2. 같은 이름인 접속.
3. 없으면 접속을 고르라고 묻고, 고른 접속을 작업에 저장한다.

비밀번호는 작업 파일에 저장하지 않는다. 기존 자격 증명 저장소(`ICredentialStore`)와 접속 대화상자를 그대로 쓴다.

### 6.4 기간

기간은 상대값으로 저장하고, 작업을 열거나 실행할 때 오늘 날짜로 다시 계산한다 **[사용자]**.

| 저장 값 | 계산 |
|---|---|
| 최근 1주 / 1달 / 3달 | `:TO_DT` = 오늘 0시 + 1일, `:FROM_DT` = 그 날짜에서 해당 기간을 뺀 날 |
| 지난달 | 지난달 1일 0시 ~ 이번 달 1일 0시 |
| 직접 지정 | 저장한 두 날짜 그대로 |
| 기간 없음 | 기간 규칙 테이블이 없을 때 |

정확한 경계 계산(오늘 포함 여부)은 **[구현]**에 맡긴다. 다만 화면에 계산한 날짜를 항상 보여야 한다.

### 6.5 저장 위치와 공유

- 작업 하나를 JSON 파일 하나로 `AppDataPaths.DataDirectory/copy-jobs/` 에 저장한다 **[사용자]**. `IAppDataPaths` 에 `CopyJobsDirectory` 를 더한다.
- 파일 이름은 작업 이름에서 만들고, 겹치면 번호를 붙인다 **[구현]**.
- 내 작업 메뉴: 새로 만들기, 복제, 이름 바꾸기, 내보내기, 가져오기, 삭제 **[사용자]**.
- 내보내기는 파일을 다른 곳에 복사하는 것이다. 가져오기는 고른 파일을 `copy-jobs/` 에 복사하고, 6.3 순서대로 접속을 다시 연결한다.
- 형식 버전이 더 높은 파일은 읽지 않고 알린다. 낮은 버전은 올려서 읽는다 **[설계]**.

## 7. 사전 점검

실행 버튼을 누르기 전에 반드시 거친다. 결과는 통과, 확인 필요, 오류 세 가지다. 오류가 하나라도 있으면 실행할 수 없다.

| 점검 | 결과 |
|---|---|
| 대상 접속 환경이 운영 | 오류(대상 목록에서부터 막는다) |
| 원본 SELECT 권한 | 없으면 오류 |
| 대상 INSERT·DELETE 권한(MERGE 면 UPDATE 도) | 없으면 오류. 대상 계정이 소유자가 아니면 `ALL_TAB_PRIVS` 등으로 테이블 권한을 확인한다 |
| 대상 테이블 없음 | 오류 |
| 열 차이: 대상에 없는 원본 열 | 확인 필요(건너뜀) |
| 열 차이: 원본에 없고 대상에서 NOT NULL·기본값 없음 | 오류 |
| 타입·길이 차이(대상이 더 짧음, 숫자 정밀도 축소) | 확인 필요 |
| 지원하지 않는 타입(8.3) | 오류 또는 열 건너뜀 선택 |
| 대상 IDENTITY `GENERATED ALWAYS` 열 | 오류 |
| 가상 열 | 통과(넣지 않음) |
| FK 순서 | 부모 → 자식으로 자동 정렬해 보여 줌. 순환이 있으면 확인 필요 |
| 대상의 자식 테이블(작업 안이든 밖이든)이 「비우고 넣기」·「같은 범위 지우고 넣기」 대상을 FK 로 참조하고, 그 자식 행이 지워지지 않고 남을 수 있음 | 확인 필요(ORA-02292 예상). 대상 처리를 MERGE 로 바꾸라고 안내한다. FK 를 끌 권한이 있을 때만 「복사하는 동안 이 FK 를 끄고 끝나면 다시 켜기」도 선택지로 보인다 **[설계]** |
| 대상 트리거 | 확인 필요. 끌 권한(소유자 또는 `ALTER ANY TRIGGER`)이 없으면 「복사한 행에도 트리거가 실행됩니다」만 알린다. 권한이 있을 때만 「복사하는 동안 끄고 끝나면 다시 켜기」를 선택지로 보인다 **[설계]** |
| 대상에만 있는 CHECK·FK 제약 | 확인 필요(실패 행이 생길 수 있음) |
| 시퀀스 보정 | 확인 필요(8.4) |
| 읽기 일관성 | 원본 `UNDO_RETENTION` 과 예상 소요 시간을 비교해 보여 줌 |
| 마스킹 | 가리는 열 목록을 보여 줌 |
| 「테이블 다시 만들기」인데 대상이 개발 접속이 아님 | 오류(`RecreateNotAllowed`) |
| 「테이블 다시 만들기」: 대상 세션이 대상 소유자가 아니거나 `CREATE TABLE`(·`CREATE TRIGGER`) 권한이 없음 | 오류(`RecreateNoPrivilege`) |
| 「테이블 다시 만들기」: 지운 뒤 원본 구조로 만들 수 없음(지원하지 않는 형식 열, `MAX_STRING_SIZE` 한도, 식이 가리키는 객체 없음, 이름 겹침) | 오류(`RecreateBlocked`) |
| 「테이블 다시 만들기」: 되돌릴 수 없음·휴지통·만들지 않는 FK·원본과 달라지는 것·되살리지 않는 것 | 확인 필요(`RecreateTable`) |
| 같은 DB 의 같은 소유자(원본 행이 지워질 수 있음) | 오류(`SameSourceTarget`) |
| 규칙이 어긋나 SQL 생성기가 문장을 만들지 못함 | 표 단위 오류(`RuleInvalid`). 그 표만 알리고 점검은 이어 간다 |

- 예상 건수는 원본에서 `COUNT(*)` 로 센다. 큰 테이블은 시간이 걸리므로 취소할 수 있어야 한다 **[설계]**.
- 오른쪽 SQL 미리 보기는 대상에서 실행할 DELETE·`DROP TABLE`(「테이블 다시 만들기」)·끄는 ALTER 문장·시퀀스를 소비하는 `SELECT … NEXTVAL` 문장과 원본 조회 조건이다. 「편집기로 열기」, 「SQL 스크립트로 저장」을 둔다.

## 8. 실행

### 8.1 세션

- 원본과 대상 각각 `ISessionManager.OpenAsync(..., SessionPurpose.Dedicated, ...)` 로 새 세션을 연다. 편집기의 작업 세션과 트랜잭션이 섞이지 않게 한다 **[설계]**.
- 원본 세션은 시작하자마자 `SET TRANSACTION READ ONLY` 를 실행하고, 모든 테이블 조회를 이 트랜잭션 하나에서 한다 **[설계]**. 이렇게 하면 추가 권한 없이 모든 테이블을 같은 시점 기준으로 읽는다. SCN 은 조회 조건(`AS OF SCN`)에도, 화면·작업 파일·실행 기록에도 쓰지 않는다 **[사용자]**. 화면에는 읽기를 시작한 시각만 보인다.
- 이 동작은 규칙 편집 화면의 「모든 테이블을 같은 시점 기준으로 읽기」(기본 켬)로 끌 수 있다 **[설계]**. 끄면 테이블마다 따로 읽으므로 ORA-01555 위험은 줄지만, 복사하는 동안 운영에서 바뀐 행 때문에 부모·자식이 어긋날 수 있다.
- 오래 걸려 ORA-01555 가 나면 그 테이블을 실패로 표시하고 멈춘다. 사용자에게 기간을 줄이거나 나눠 실행하라고 안내한다.

### 8.2 순서

1. 사전 점검에서 끄기로 고른 트리거와 FK 가 있으면 끈다(`ALTER TRIGGER ... DISABLE`, `ALTER TABLE ... DISABLE CONSTRAINT`). 권한이 없어 고르지 않았다면 이 단계와 5단계는 건너뛴다.
2. 대상 정리: 자식 → 부모 순서로 DELETE 한다(대상 처리가 「비우고 넣기」·「같은 범위 지우고 넣기」인 테이블). 「테이블 다시 만들기」인 테이블은 보존할 DDL 을 받아 둔 뒤 자식 → 부모 순서로 지우고, 부모 → 자식 순서로 새로 만든다(6.2.3).
3. 적재: 부모 → 자식 순서로 테이블마다 원본을 스트리밍으로 읽어 배치로 넣는다.
4. 시퀀스를 보정한다.
5. 끈 FK 와 트리거를 다시 켠다. 이 단계는 실패·중지·예외가 나도 반드시 실행한다(`finally`). FK 는 `ENABLE VALIDATE` 로 켜고, 부모 없는 자식 행 때문에 실패하면 `ENABLE NOVALIDATE` 로 켠 뒤 그 FK 와 부모 없는 행 수를 결과에 보인다 **[설계]**.
6. 건수 비교: 원본 건수는 적재할 때 읽은 행 수, 대상 건수는 같은 조건으로 대상에서 `COUNT(*)` 한 값이다.

- 「같은 범위 지우고 넣기」의 대상 쪽 범위는 대상 테이블에서 같은 조건으로 계산한다. 부모 키 규칙이면 대상의 부모 테이블 기준이다.
- 지난번 복사 뒤 원본에서 기간 열 값이 바뀐 행은, 대상에 옛 범위로 남아 있어 지워지지 않고 PK 충돌(ORA-00001)을 낸다. 그 행을 PK 로 먼저 지우면, 대상에 남은 옛 자식 행 때문에 ORA-02292 가 나고 대상 계정은 FK 를 끌 수 없다(2장). 그래서 PK 가 있는 테이블은 범위 DELETE 뒤의 적재를 INSERT 가 아니라 PK 기준 MERGE(있으면 UPDATE, 없으면 INSERT)로 하고, 이것도 바인드 배열로 실행한다 **[설계]**. 자식 테이블도 같다. 옛 범위에 남은 자식 행은 지워지지 않고 남지만 실패하지는 않는다. PK 가 없는 테이블은 이 처리를 하지 않고 사전 점검에서 「PK 없음: 다시 실행하면 행이 겹칠 수 있음」을 확인 필요로 보인다.
- 커밋 단위: 테이블마다(기본), 배치마다, 모두 끝난 뒤 한 번 **[설계]**. 「모두 끝난 뒤 한 번」은 실패하면 전부 되돌린다. 나머지는 이미 커밋된 테이블이 남지만 다시 실행하면 같은 결과가 된다.
- 일시 정지는 배치와 배치 사이에서 멈춘다. 중지는 현재 배치를 되돌리고 5단계(트리거 켜기)를 거친 뒤 끝낸다.
- 실패한 배치는 지금 가져오기(`OracleDataTransferService.InsertBatchAsync`)처럼 한 행씩 다시 넣어 실패한 행을 찾는다. 실패 행이 정해진 수(기본 100)를 넘으면 그 테이블을 멈춘다 **[설계]**.
- 「실패 행만 다시 넣기」는 기록해 둔 실패 행 키로 원본에서 다시 읽어 넣는다 **[설계]**. 실패 행 값을 메모리에만 두면 앱을 닫을 때 사라지므로, 키로 다시 읽는 방식을 쓴다.

### 8.3 쓰기 경로와 타입

- 지금 가져오기는 값을 리터럴로 바꾼 `INSERT ... SELECT ... FROM DUAL UNION ALL` 문장을 만든다. 복사는 행이 많고 LOB 도 다루어야 하므로 **바인드 배열(array binding)** 로 넣는다 **[설계]**.
- 그래도 모든 쓰기는 정책 관문을 지나야 한다(4장). 문장 하나(같은 SQL 텍스트)에 대해 정책을 한 번 평가하고, 그 문장을 바인드 배열로 여러 번 실행하는 경로를 실행 엔진에 더한다 **[설계]**. 구체적인 API 모양은 **[구현]**.
- 정책이 `Confirm` 을 내는 문장(예: WHERE 없는 DELETE)은 사전 점검 화면에서 한 번에 보여 주고 사용자가 「복사 실행」을 누른 것을 확인으로 본다 **[설계]**. `Deny` 면 실행하지 않는다. 이를 위해 이력 출처(`HistorySource`)에 복사용 값을 더할지는 **[구현]**.
- 이력: 대상에 실행한 DELETE·ALTER 문장은 실행 이력에 남긴다. 행마다 실행하는 INSERT 는 남기지 않는다 **[설계]**.
- 1차 지원 타입: 문자(VARCHAR2·CHAR·NVARCHAR2·NCHAR), NUMBER·BINARY_FLOAT·BINARY_DOUBLE, DATE·TIMESTAMP 계열, INTERVAL, RAW, CLOB·NCLOB·BLOB **[설계]**.
- 1차 미지원: LONG·LONG RAW, BFILE, XMLTYPE, 객체·컬렉션 타입, VECTOR, JSON(21c 이상 네이티브 타입). 사전 점검에서 오류로 보여 주고 「이 열 건너뛰기」를 고를 수 있게 한다.
- 열은 이름으로 대응시킨다. 숨김 열(`IsInvisible`)도 이름을 명시해 복사한다. 가상 열은 넣지 않는다.

### 8.4 시퀀스 보정

- 시퀀스와 열의 연결은 DB 에서 알 수 없다. 사전 점검이 이름 규칙(`SEQ_<열 이름>`, `<테이블>_SEQ` 등)으로 후보를 제안하고, 사용자가 확인하면 작업 파일에 저장한다 **[설계]**.
- 복사가 끝난 뒤 대상 시퀀스의 다음 값이 그 열의 최대값보다 작으면 최대값 + 1 이상으로 앞당긴다.
- 대상 계정은 `ALTER SEQUENCE` 권한이 없을 수 있으므로(2장), 기본 방법은 `NEXTVAL` 을 모자란 수만큼 호출하는 것이다 **[설계]**. 시퀀스 SELECT 권한만 있으면 되고, `SELECT 시퀀스.NEXTVAL FROM DUAL CONNECT BY LEVEL <= :n` 처럼 한 번에 여러 개를 소비해 왕복을 줄인다. 한 번에 소비하는 개수와 상한은 **[구현]**.
- 모자란 수가 매우 크면(기본 1,000만 이상) 시간이 걸린다고 사전 점검에서 알리고 사용자에게 진행 여부를 묻는다 **[설계]**.
- 시퀀스 SELECT 권한이 없으면 보정하지 않고 「테스트 중 PK 충돌이 날 수 있음」만 알린다.
- 시퀀스 값은 내리지 않는다.

### 8.5 마스킹

- 마스킹은 원본에서 읽은 값을 대상에 넣기 전에 클라이언트에서 바꾼다 **[설계]**. 원본에 함수를 만들 권한이 없어도 되기 때문이다.
- 규칙: 고정값으로 바꾸기, 앞 n 글자만 남기기, 뒤 n 글자만 남기기, 같은 입력이면 같은 출력이 나오는 해시, NULL **[설계]**.
- 같은 값이 여러 테이블에서 조인 키로 쓰이면 해시 규칙을 써야 조인이 유지된다. 이 안내를 마스킹 규칙 화면에 둔다.
- PK·UK 열과 부모 키 규칙의 연결 열에는 마스킹을 걸 수 없다(사전 점검 오류) **[설계]**. 이렇게 하면 「실패 행만 다시 넣기」, PK 기준 MERGE, 8.2 의 PK 충돌 처리, 부모 키 조건이 모두 원래 값으로 동작하고, 실행 기록의 키 열에도 마스킹 대상 값이 들어가지 않는다.
- 해시 규칙은 문자 열에만 쓴다. 결과는 16진수 문자열을 대상 열 길이에 맞춰 자른다. 숫자·날짜 열은 고정값과 NULL 규칙만 쓴다 **[설계]**.
- 해시의 비밀 값(salt)은 작업마다 하나를 만들어 작업 파일에 저장한다 **[설계]**. 작업을 내보내 동료와 주고받으면 같은 비밀 값을 쓰게 되어, 서로 복사한 데이터끼리도 조인이 맞는다. 비밀 값이 없는 해시는 전화번호처럼 경우의 수가 적은 값을 쉽게 되돌릴 수 있으므로 쓰지 않는다.
- 열 이름 규칙(`docs/idea.md` 「민감 컬럼 가림」)과 합치는 것은 이후 작업이다.

## 9. 실행 기록

- 실행할 때마다 `LogsDirectory/copy-runs/` 에 기록 파일 하나를 남긴다 **[설계]**: 작업 이름, 원본·대상 접속 이름, 기간, 테이블별 건수·소요 시간·결과, 실행한 DDL·DELETE 문장, 실패 행의 **키 열과 오류 메시지**.
- 행 값은 남기지 않는다(4장). 실패 행 값을 CSV 로 저장하는 것은 사용자가 「CSV로 저장」을 눌렀을 때만 한다.
- 실패 행의 키 열 값은 남긴다. 「실패 행만 다시 넣기」가 키로 원본을 다시 읽기 때문이다. 키 열에는 마스킹을 걸 수 없으므로(8.5) 마스킹 대상 값은 기록에 들어가지 않는다.
- 실행이 끝나지 않은 기록(앱 강제 종료)이 있으면, 다음에 그 작업을 열 때 「지난 실행이 끝나지 않았습니다. 대상 트리거·FK 상태를 확인하세요」와 함께 꺼 두었던 트리거와 FK 목록을 보여 주고 「다시 켜기」를 제공한다 **[설계]**.

## 10. 화면

시안 3장을 따른다. 시안과 달라지는 부분:

- 규칙 표의 조건 칸은 기간 열과 형식을 보인다(예: `ORDER_DT · YYYYMMDD 문자열`). 실제 비교는 시작 포함·끝 제외다(6.2).
- 기간 규칙을 고른 테이블의 오른쪽 패널에는 시안에 없는 조작이 필요하다: 「생성 시각」 표시가 붙은 기간 열 고르기, 문자열 형식 고르기, OR 로 묶을 두 번째 열(선택)(6.2.1, 6.2.2).
- 「비우고 넣기」의 SQL 미리 보기는 TRUNCATE 가 아니라 DELETE 다(6.2).
- 원본 접속 버튼에 「읽기 전용」 표시는 원본 세션이 읽기 전용 트랜잭션으로 열린다는 뜻으로 그대로 둔다.
- 대상 접속 목록에서 운영 접속은 비활성으로 보이고 이유를 툴팁으로 알린다.

밀도와 아이콘은 Oranda 의 다른 창(가져오기 대화상자, DDL 추출)과 맞춘다 **[구현]**.

## 12. 시험

- 단위 시험: 기간 계산, 문자열 날짜 형식별 경계 문자열 생성과 열 길이로 형식 추정, 규칙 → 원본 조건·대상 DELETE 생성(부모 키 여러 단계 포함, 문자열 날짜 포함), FK 위상 정렬과 순환 감지, 작업 파일 직렬화·버전 올림, 접속 다시 연결 순서, 마스킹 함수, 운영 대상 차단.
- 통합 시험: 시험 DB 컨테이너 하나 안에 원본 사용자와 대상 사용자 두 스키마를 만들어 복사한다. 컨테이너를 더 띄우지 않는다. 통합 시험은 CI 에서 돌린다.
  - 전체·기간(DATE 열, TIMESTAMP 생성 시각 열, 문자열 열, 두 열 OR)·부모 키·제외 규칙, 다시 실행해도 같은 결과, LOB 열, 트리거 끄고 켜기(실패 중에도 켜지는지), 시퀀스 보정(`NEXTVAL` 소비), 대상에만 있는 CHECK 제약으로 실패 행 생성, 읽기 전용 대상 프로필 거부.
  - 대상 접속 계정이 소유자가 아니고 테이블 INSERT·UPDATE·DELETE·SELECT 권한만 받은 경우: 기본 동작이 모두 되고, 트리거·FK 끄기 선택지는 보이지 않아야 한다.
  - 테이블 다시 만들기: 개발 라벨 대상에서만 선택지가 보이는지, 원본 구조대로 만들어지는지, 대상에 있던 트리거·권한·참조 FK 가 되살아나는지, 휴지통에서 되돌릴 수 있는지, 테스트 라벨 대상에서는 DROP 이 거부되는지.
- 시험 데이터와 접속 이름은 예시 값만 쓴다(`APP@PROD` 같은 이름도 시험 코드에서는 쓰지 않고 시험용 사용자 이름을 쓴다).

## 13. 구현 결정

설계 당시 구현자에게 맡겼던 항목(13.1)과, 구현이 설계·계획과 달라진 곳(13.2), 알려진 한계(13.3)를 적는다. 필드 이름과 파일 형식의 정본은 `docs/design/data-model.md` 의 2.7·2.8 이다.

### 13.1 계획에서 정한 것

- **대량 실행 API**: `IBulkExecutionService.StreamRowsAsync`(원본 읽기, 정책 한 번 평가, 실효 분류가 조회가 아니면 `BulkDeniedException`)와 `ExecuteArrayAsync`(같은 SQL 텍스트에 정책을 한 번 평가하고 `ArrayBindCount` 로 한 번에 실행). 원본 읽기도 모두 `StreamRowsAsync` 를 쓰고 원본에 `IExecutionService` 를 쓰지 않는다. 정책 단계는 `PolicyGate` 로 뽑아 `OracleExecutionService` 와 함께 쓴다. `StatementExecuted` 이벤트는 `ExecuteArrayAsync` 한 번에 하나만 내고, 복사 문장의 이력은 `HistorySource.DataCopy` 와 `ExecutionOptions.SkipHistory` 로 가른다. `BindDataType.TimestampLtz` 를 더했다. LOB 은 끝까지 읽어 같게 넣는다.
- **정책 확인을 모아 받는 방법**: `ExecutionOptions.PreConfirmed`(호출한 쪽이 이미 확인을 받은 문장 텍스트의 서수 비교 집합). 정책이 `Confirm` 이고 텍스트가 집합에 있으면 `IExecutionInteraction` 을 부르지 않는다. `Deny` 는 그대로 거부한다. `RetypeText` 가 있는 `Confirm`(`DROP`)도 집합에 있으면 통과하는데, 그 전에 화면이 대상 접속 이름을 다시 입력받는다(6.2.3). 미리 보기와 실행기는 `CopyStatements` 로 같은 글자의 문장을 만들어야 집합이 맞는다.
- **작업 파일 필드 이름**: 계획 T1 의 `CopyJob` 레코드 그대로(camelCase). 형식은 `data-model.md` 2.7, `CopyJobSchema.Current` = 1.
- **기간 경계**: 시작 포함·끝 제외. 「최근 1주·1달·3달」은 내일 0시를 끝으로 거꾸로 센다(오늘 포함). 「지난달」은 지난달 1일 0시부터 이번 달 1일 0시 전까지다. 일 단위가 없는 `YYYYMM` 형식의 끝 경계는 끝이 달의 1일 0시면 그 달, 아니면 다음 달이다. 문자열 날짜 형식 토큰은 `YYYY`·`MM`·`DD`·`HH24`·`MI`·`SS` 만 받고 구분자는 `-`·`/`·`:`·`.`·공백만 허용한다(`MON` 은 받지 않는다).
- **시퀀스 보정**: 사전 점검은 `NEXTVAL` 을 부르지 않고 `LAST_NUMBER` 와 원본 범위의 최대값으로 어림한다. 실행은 `NEXTVAL` 을 한 번 불러 현재 값을 알고, 모자란 수를 `SELECT 시퀀스.NEXTVAL FROM DUAL CONNECT BY LEVEL <= :N` 로 10,000개씩 소비한다. 버전별로 다른 방법은 두지 않았다(18c 미만 분기 없음). 읽기 전용 대상, 적재를 확정하지 못한 표는 건너뛴다.
- **화면 세부**: 「도구 > 데이터 복사…」 단축키는 없다(메뉴와 명령 팔레트). 아이콘 단추는 기존 `.toolbar` 스타일을 쓴다.
- **실패 행 키 글자**: TIMESTAMP 는 소수 7자리(100ns)로 쓰고, 그보다 작은 자리가 있으면(`TIMESTAMP(8)`·`TIMESTAMP(9)`) 9자리로 쓴다.

### 13.2 설계·계획과 달라진 곳

| 번호 | 내용 |
|---|---|
| 1 | 권한 점검: 계획의 `USER_SYS_PRIVS` 대신 `SESSION_PRIVS` 와 `ALL_TAB_PRIVS`(사용자·`PUBLIC`·활성 롤)를 쓴다(조정 승인). |
| 2 | 점검 코드 추가: `RuleInvalid`(표 단위 규칙 오류), `SameSourceTarget`(같은 DB·같은 소유자), `RecreateNotAllowed`, `RecreateNoPrivilege`, `RecreateBlocked`, `RecreateTable`(7장). `RuleInvalid` 는 T10 이 들어오기 전까지 「테이블 다시 만들기」 규칙을 막는 임시 오류로도 썼다(T10 에서 제거). 구현 중간에 있던 `RecreateMissingObject`(식이 가리키는 객체가 없음)는 `RecreateBlocked` 로 합쳤고 최종 코드에는 없다. |
| 3 | 같은 DB 판정은 접속 식별자(`DbKey`)의 앞 두 마디에 호스트·인스턴스 이름을 더해 비교한다(RAC 는 이름만, 모르면 같다고 본다). 이름만 비교하면 복제 DB·기본 이름 컨테이너가 서로 같게 보이기 때문이다. |
| 4 | `DROP TABLE` 에 `CASCADE CONSTRAINTS` 를 붙이지 않는다(6.2.3). 대상 계정에 보이지 않는 다른 스키마의 FK 를 말없이 지우지 않으려는 것이다. 받아 둔 참조 FK 를 먼저 떼어 낸 뒤 지우고, 보이지 않는 FK 가 남아 있으면 서버가 `ORA-02449` 로 거부해 그 표를 지우지 않고 멈춘다. 떼어 낸 FK 는 끝낼 때 되붙인다. |
| 5 | 보존 DDL 을 받는 방법: 트리거 본문만 `DBMS_METADATA.GET_DDL` 로 받고, 권한과 참조 FK 는 카탈로그(`ALL_TAB_PRIVS`, `ALL_CONSTRAINTS`, `ALL_CONS_COLUMNS`)로 문장을 만든다. 자식 표가 다른 스키마에 있으면 `GET_DDL('REF_CONSTRAINT')` 에 `SELECT_CATALOG_ROLE` 이 필요하기 때문이다. |
| 6 | 「테이블 다시 만들기」 권한은 대상 세션이 대상 소유자일 때만 허용한다(설계 초안의 「그에 준하는 권한」보다 좁다). 비소유자는 트리거 DDL 을 받거나 권한을 되살리는 데 더 큰 권한이 필요해 지운 뒤 되살리지 못할 수 있다. |
| 7 | 작업 안 표끼리의 FK 는 `CreateTableDdl` 의 열 목록 없는 FK 대신 원본 카탈로그(`ON DELETE`·`DEFERRABLE`·꺼짐·UK 참조)로 만들고, 모든 표를 적재한 뒤 붙인다. 자기 참조나 서로 참조 표에서 자식 행이 부모 행보다 먼저 와도 실패하지 않게 하려는 것이다. 부모 없는 행이 있으면 `ENABLE NOVALIDATE` 로 켜고 행 수를 알린다. |
| 8 | 지우기 전 확인: `RecreateTable`(확인 필요, 휴지통·되돌릴 수 없음·만들지 않는 FK·원본과 달라지는 것·되살리지 않는 것)과, 지운 뒤에야 드러나는 `CREATE` 실패(표가 휴지통에만 남음)를 지우기 전에 막는 `RecreateBlocked`. |
| 9 | 지우기 전에 보존 DDL 과 지울 표 목록을 실행 기록(디스크)에 쓰고, 쓰지 못하면 아무 표도 지우지 않는다. 기록 형식은 `data-model.md` 2.8 의 「-- 보존 DDL」 `statement` 줄이다. |
| 10 | 이 세션에서 `ALTER SESSION SET RECYCLEBIN = ON` 을 먼저 보낸다. DB 기본이 꺼져 있으면 `PURGE` 가 없어도 영구 삭제되기 때문이다. 표가 휴지통을 지원하지 않는 테이블스페이스에 있으면 영구 삭제된다고 알린다. |
| 11 | 대상에 없는 표를 새로 만드는 「테이블 다시 만들기」는 지원하지 않는다(`TargetMissing` 오류 그대로). |
| 12 | 시퀀스 후보는 점검 통과 항목의 「작업에 연결」 체크로 사용자가 연결한다. 연결한 시퀀스만 작업 파일 `sequences[]` 에 저장된다. |
| 13 | 별도 창(데이터 복사)에는 F1 매뉴얼 연결이 없다. 창 안의 포커스 자리를 `FocusScopes` 에 등록하지 않았다. |
| 14 | 결과에서 뺀 실패 행(적재를 끝내지 못한 표의 행)이 실행 기록에는 남을 수 있다. 「배치마다 커밋」에서 앞 배치를 커밋할 때 이미 `failedRow` 로 썼기 때문이다. 그 표의 `table` 줄 메시지가 이 행들을 덮는 것으로 본다. |

### 13.3 알려진 한계

- 시퀀스 보정의 RAC 분기(`LAST_NUMBER` 하한을 쓰지 않는 경우)는 시험하지 못했다. 통합 시험 컨테이너가 단일 인스턴스다.
- 함께 다시 만든 표는 FK 없이 적재하므로 부모 없는 행은 실패 행이 아니라 `NOVALIDATE` 알림과 행 수로만 보인다. 트랜잭션을 끝내지 못해 작업 안 FK 를 붙이지 못한 뒤 다시 실행하거나 재시도하면 부모 없는 행도 들어가고, 알림에 나온 FK 문장을 직접 실행하면 `ORA-02298` 이 날 수 있다.
- 지우기 전에 받아 둔 보존 DDL(트리거·권한·참조 FK) 전체는 실행 기록 파일에만 있다. 되살리지 못한 문장만 알림과 표 결과에 원문으로 나온다. 미완료 실행 화면에는 끈 트리거·FK 만 나오고 보존 DDL 은 나오지 않는다(후속). `DROP` 뒤 앱이 죽으면 기록 파일의 줄을 직접 실행해야 하고, 휴지통에서 `FLASHBACK` 하면 트리거·인덱스·권한은 함께 돌아오지만 참조 FK 는 돌아오지 않는다.
- 다른 계정이 소유한 자식 표의 FK, 열 권한, 트리거는 대상 소유자 계정에 보이지 않을 수 있다. 보이지 않는 FK 가 표를 참조하면 지우지 않고 멈춘다.
- 이름 겹침 검사는 함께 다시 만드는 표의 이름을 모두 지운 뒤 만든다고 가정한다. 표 A·B 사이에 이름이 겹치는데 B 의 `DROP` 이 멈추면 이미 지운 A 의 `CREATE` 가 `ORA-00955` 로 실패해 A 는 휴지통에만 남는다(아주 드물다).
- 끄거나 되살릴 FK 를 이름만으로 정한다(`DisabledObject.Name`). `ALTER ANY TABLE` 권한이 있는 계정에서 다른 스키마에 같은 이름의 자식 FK 가 같은 표를 참조할 때만 어긋난다.
- 별도 창(데이터 복사)에는 F1 매뉴얼 연결이 없다. 창 안의 포커스 자리를 `FocusScopes` 에 등록해야 하며, 데이터 내보내기·가져오기 창도 같다(후속).
- 조회 전용 역할(viewer)에도 「데이터 복사」 메뉴가 보인다. 쓰기는 정책 관문이 거부한다. 메뉴를 숨길지는 정해지지 않았다.
- 자기 참조 통합 시험은 저장 순서(`ORDER BY` 없음)에 기대고 있다.
