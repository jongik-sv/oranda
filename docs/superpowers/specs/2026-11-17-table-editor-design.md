# 테이블 편집기 설계 (객체 상세에서 바로 고치기 · 새 테이블 · 반영 묶음)

작성일: 2026-11-17. 상태: 설계(구현 전). 관련: `docs/idea.md` 1장(테이블 구조 편집), PRD 2.2(마법사는 이후로 미뤘던 항목), SAFE-03 운영 확인, TSK-13-07 변경 일지, 열 순서 바꾸기(`ColumnReorder`), 데이터 복사(`CreateTableDdl`).

표기: **[사용자]** = 사용자가 정함, **[설계]** = 시안으로 보여 주고 사용자가 이의 없이 넘어감, **[설계자 결정 TE-n]** = 설계자가 이 문서에서 정함(사용자가 뒤집을 수 있음, 목록은 16장), **[구현]** = 구현자에게 맡김.

시안(브레인스토밍 화면, 정본): `docs/superpowers/specs/2026-11-17-table-editor-mockups.html`. 화면 0 편집 위치 A/B, 화면 ① 새 테이블, ② 반영 묶음 창, ③ 제약 편집, ④ 인덱스 편집, ⑤ 가상 식 미리보기와 실행 전 검사. 이 문서는 시안을 정본으로 삼고, 시안이 정하지 않은 동작과 모듈 경계를 더한다.

## 1. 목적과 이유

Oranda 에는 테이블을 만들거나 구조를 고치는 화면이 없다. 객체 상세는 읽기 전용이고(`DetailTable` 은 표시만 한다), 바꾸려면 SQL 편집기에 `ALTER TABLE` 을 손으로 쓴다. 가상 열은 읽고 보여 주지만(`ColumnInfo.IsVirtual`, 상세 「열」의 「가상」 칸) 만드는 길이 없다.

사용자의 일하는 방식 **[사용자, 2026-11-17]**:

- 테이블 구조 변경은 대부분 개발 DB 에서 하고, 테스트 DB 에 적용해 본다.
- 운영 중인 시스템의 운영 DB 변경은 DB 관리 팀에 「의뢰서」(결재 문서)로 요청한다. 개발 쪽이 스크립트를 다 만들고, 그 팀은 실행만 한다.
- 의뢰서 스크립트는 **DDL 만** 넣고, **여러 건을 한 파일**로 묶는다.
- 신규 시스템은 운영 DB 에서도 테이블 편집을 많이 한다(아직 서비스 전이라 직접 실행한다).

그래서 이 기능은 두 가지를 같이 만든다.

1. **테이블 편집기**: 객체 상세에서 편집을 켜고 열·제약·인덱스를 표에서 고치면, 바뀐 만큼의 DDL 이 아래에 바로 보이고 실행·스크립트 저장·묶음 넣기를 한다. 새 테이블도 같은 화면(빈 상세 탭)에서 만든다.
2. **반영 묶음**: 개발 중에 실행한 DDL(테이블 편집기에서 나온 것과 SQL 편집기에서 직접 실행한 것)을 이름 붙인 묶음에 모으고, 개발·테스트·운영 중 어디까지 실행했는지 표시하고, 체크한 문장만 의뢰용 `.sql` 한 파일로 저장한다.

## 2. 목표

- 기존 테이블의 객체 상세 「열」「제약」「인덱스」 페이지에서 ✎ 편집을 켜고 표에서 고친다. 바뀐 칸은 노랑, 새 줄은 초록, 지울 줄은 빨강 줄긋기로 보인다 **[설계, 화면 0 A]**.
- 고친 내용은 그 즉시 페이지 아래 DDL 미리보기에 문장으로 나온다. 사용자가 DDL 을 보지 않고 실행하는 길은 없다.
- 열: 추가, 지우기, 이름 바꾸기, 형식·길이·정밀도·소수 자리 바꾸기, NULL 허용 바꾸기, 기본값 바꾸기, 주석 바꾸기, 가상 열 추가(가상 식 입력) 와 가상 식 바꾸기.
- 제약: PK·UK·FK·CHECK 추가, 지우기, 사용/사용 안 함(ENABLE/DISABLE) 바꾸기 **[설계, 화면 ③]**.
- 인덱스: 일반·유일 인덱스 추가, 지우기, 열 구성(순서·ASC/DESC) 바꾸기. 열 구성 변경은 DROP + CREATE 두 문장이다 **[설계, 화면 ④]**.
- 테이블 주석 바꾸기.
- 새 테이블: 스키마 브라우저에서 「새 테이블…」로 빈 객체 상세 탭을 편집 모드로 열고, 열·제약·인덱스를 넣어 `CREATE TABLE` + `COMMENT` + `CREATE INDEX` 를 만든다. 실행하면 그 탭이 실제 테이블 상세로 바뀐다 **[설계, 화면 ①]**.
- 「이 구조로 새 테이블…」: 고른 테이블의 열·주석·제약·인덱스를 복사해 새 테이블 편집을 시작한다. 이름은 새 테이블 이름으로 다시 만든다 **[설계, 화면 ①]**.
- 가상 식을 고치면 실제 데이터 5줄로 계산해 미리 보여 준다 **[설계, 화면 ⑤]**.
- 실행·묶음 넣기 전에 데이터를 읽어 검사한다. 실패가 확실한 것(✖)은 막고, 위험(⚠)은 알리기만 한다 **[사용자, 2026-11-17]**.
- 제약·인덱스 이름은 규칙대로 미리 채운다: `PK_<테이블>`, `UK_<테이블>_NN`, `FK_<테이블>_NN`, `CK_<테이블>_NN`, `IX_<테이블>_NN` **[사용자, 2026-11-17 「그대로」]**. 사용자는 고칠 수 있다.
- 반영 묶음: 아래 도구 창(변경 일지 옆). 지금 묶음 고르기·새 묶음·이름 바꾸기·지우기, 문장 순서 바꾸기·빼기(체크 해제)·지우기, 접속을 골라 실행, 의뢰용 스크립트 저장 **[사용자: 방식 A, 2026-11-17]**, **[설계, 화면 ②]**.
- SQL 편집기에서 DDL 을 실행해 성공하면, 「지금 묶음」이 있을 때 그 묶음에 자동으로 쌓인다 **[사용자, 2026-11-17]**.
- 묶음의 문장마다 개발·테스트·운영 접속에서 마지막으로 성공한 날짜를 표시한다 **[설계, 화면 ②]**.
- 실행은 모든 환경에서 된다. 개발·테스트는 「실행」이 기본 단추다. 운영은 SAFE-03 확인을 거쳐 실행할 수 있고, 실행 전 검사가 「의뢰용 스크립트 저장」을 권한다 **[설계]** (신규 시스템은 운영에서도 직접 고친다는 사용자 말에 따름).
- Oracle 과 Tibero 가 첫 배포부터 같은 기능 수준이다(2026-11-09 Tibero 완전 지원 결정, D-03 뒤집음). 차이는 방언과 실측 항목에서만 다룬다(12장).

## 3. 비목표 (첫판에서 뺌) **[사용자, 2026-11-17]**

- 파티션 만들기·고치기(파티션 테이블은 고칠 수 있지만 파티션 정의는 건드리지 않는다).
- 저장 속성(테이블스페이스 지정 외 PCTFREE·INITRANS·STORAGE·압축 등). 테이블스페이스는 접속 기본값을 쓰고, 고칠 때만 칸을 연다.
- LOB 저장 절(`LOB (…) STORE AS …`).
- 테이블 이름 바꾸기.

그 밖에 첫판에서 다루지 않는 것 **[설계자 결정 TE-1]**:

- 기존 열의 순서 바꾸기. 이미 있는 「열 순서 바꾸기…」 창으로 넘긴다(편집 도구줄의 ↑↓ 는 아직 실행하지 않은 새 열과 새 테이블에서만 켜진다).
- 열 형식 변경을 위한 자동 데이터 변환(새 열 만들고 복사하고 바꿔치기). 검사에서 ✖ 로 막고 이유만 보여 준다.
- 임시 테이블(GTT)·외부 테이블·IOT·클러스터 테이블의 생성. 기존 그런 테이블은 열 주석·기본값만 고칠 수 있고 나머지 편집 단추는 흐리게 둔다 **[구현: 판정 기준]**.
- 시퀀스·트리거·동의어·권한 편집(`docs/idea.md` 2.3 의 다른 「만들기」 항목).
- 두 DB 구조 비교로 스크립트 만들기(스키마 비교). 반영 묶음 방식 C 로 검토했고 별도 프로젝트로 둔다.
- 개발 DB 가 Oracle 이고 운영 DB 가 Tibero 인 것처럼 DBMS 가 섞인 묶음(TE-23).

## 4. 반목표 (이렇게 되면 실패)

- 사용자가 본 DDL 미리보기와 실제로 실행되거나 저장되는 문장이 다르다.
- 편집에서 바꾸지 않은 열·제약·인덱스에 대한 문장이 생긴다(예: 형식 표기 차이 `NUMBER` vs `NUMBER(*,0)`, 기본값 공백 차이, `CHAR`/`BYTE` 길이 기준 차이로 거짓 MODIFY 가 나온다).
- 의뢰용 스크립트에 DML·SELECT·시험용으로 실행한 DDL 이 사용자 모르게 섞인다. 저장 파일은 체크한 묶음 문장만, 화면에 보이는 순서대로 담는다.
- 실행 전 검사가 운영 테이블을 오래 잠그거나 서버를 무겁게 한다. 검사는 읽기만 하고, 시간 제한을 넘기면 「확인 못 함」 ⚠ 로 끝난다.
- 실패가 확실한 DDL 을 운영에 실행해, 앞 문장만 반영되고 뒤 문장이 실패한 반쪽 상태가 된다(DDL 은 문장마다 자동 커밋이라 되돌릴 수 없다).
- SQL 편집기의 DDL 이 실패했는데 묶음에 들어간다. 또는 묶음에서 실행한 문장이 다시 묶음에 겹쳐 들어간다.
- 편집 모드가 켜진 채 다른 일을 하다가 고친 내용을 말없이 잃는다(탭 닫기·다른 페이지로 가기·새로 고침).

## 5. 제약

- 사용자에게 보이는 쓰기(편집기 실행, 묶음 실행)는 지금처럼 실행 엔진 `IExecutionService`(`src/Oranda.Core/Execution/IExecutionService.cs:12`)의 정책 관문을 지난다. 운영은 SAFE-03 확인(`ExecutionPolicy.cs:155-160`)이 뜬다.
- 운영에서 여러 문장을 실행할 때 확인 창이 문장마다 뜨지 않게 한다. 열 순서 바꾸기처럼 `AsSingleBlock`(문장을 `EXECUTE IMMEDIATE` 로 감싼 PL/SQL 블록 하나)으로 묶지 **않는다**. 그러면 문장 종류가 `PlSql` 이 되어 묶음 자동 넣기(9.3), 문장별 실행 표시(9.1), 남은 문장 다시 계산(TE-5), 변경 일지의 문장별 이전 DDL 이 모두 깨진다. 대신 확인을 한 번 받은 뒤 데이터 복사처럼 `ExecutionOptions.PreConfirmed`(`CopyRunner.State.cs:578`)로 문장을 하나씩 보낸다. 확인 창 문구에 「앞 문장이 성공한 뒤 뒤 문장이 실패하면 앞 문장은 남는다(DDL 자동 커밋)」를 적는다 **[설계자 결정 TE-21]**, **[구현: 문구]**.
- DDL 은 Oracle·Tibero 모두 열린 트랜잭션을 암묵적으로 커밋한다. 편집기 실행 전에 그 세션에 커밋하지 않은 변경이 있으면 지금 실행 엔진이 하는 경고를 그대로 따른다 **[구현: 기존 경고 재사용 여부 확인]**.
- 실행 전 검사와 가상 식 미리보기의 읽기 문장(`SELECT COUNT(*)`, `MAX(LENGTH(…))` 등)은 사용자 문장이 아니다. 실행 이력·변경 일지·반영 묶음에 남기지 않는다. 정책 관문 확인 창도 띄우지 않는다(Query 라 원래 뜨지 않는다). 세션 명령 잠금(D-041)을 다시 잡아 교착되지 않게, 실행 엔진 밖에서 메타데이터 공급자처럼 별도 경로로 읽는다 **[구현: 경로 선택, 되돌리기 지점 설계 5장의 `IRollbackChannel` 판단 참고]**.
- Core 는 다른 Oranda 어셈블리를 참조하지 않는다(`LayerDependencyTests`). 「바뀐 내용 → DDL」 은 Core 에 두고, DBMS 차이는 Oracle·Tibero 공급자의 방언으로 넘긴다.
- 의미 판단은 오류 번호가 아니라 `DbErrorKind` 로 한다(D-046).
- 시험 데이터·접속 이름은 예시 값만 쓴다(`dev-example`, `SAMPLE.ORDERS`, `SAMPLE.ORDER_ITEMS`). 회사 DB 별칭·호스트·IP 는 시험·문서·커밋에 넣지 않는다.
- 반영 묶음에는 DDL 전문이 이 PC 의 `oranda.db` 에 평문으로 남는다. DDL 에는 행 데이터가 없지만 CHECK 조건·기본값에 리터럴이 있을 수 있다. 변경 일지가 `previous_ddl` 을 평문으로 두는 것과 같은 수준으로 본다 **[설계자 결정 TE-2]**.

## 6. 접근 방식 (검토한 것과 고른 것)

### 6.1 어디서 고칠까 — **A 객체 상세에서 바로 편집** **[사용자, 2026-11-17]**

- **A. 객체 상세에서 바로 편집** (결과 그리드 편집 모드처럼, 연필 단추로 켬). 보는 곳 = 고치는 곳. 제약·인덱스 페이지도 같은 방식. 단점: 새 테이블은 상세가 없어 빈 상세 탭을 따로 열어야 하고, 보기 화면이 편집 단추로 조금 복잡해진다.
- B. 별도 「테이블 편집」 문서 탭 (Orange Create/Alter Table, SQL Developer Edit Table 방식). 새 테이블과 고치기가 같은 화면이고 상세는 읽기 전용으로 남는다. 설계자는 B 를 추천했다.
- 사용자는 A 를 골랐다. 보다가 바로 고치는 흐름이 중요하다는 판단이다. A 의 단점은 「새 테이블 = 빈 상세 탭」(화면 ①)으로 푼다.

### 6.2 여러 건을 한 파일로 — **A 반영 묶음 + SQL 편집기 DDL 자동 넣기** **[사용자, 2026-11-17]**

- **A. 반영 묶음**: 편집기 실행 또는 「묶음에 넣기」로 이름 붙인 묶음에 쌓고, 순서를 맞추고 빼서, 테스트에 실행하거나 의뢰용 `.sql` 로 저장한다. 개발 → 테스트 → 의뢰 흐름이 그대로 화면이 된다. 단점: 어느 묶음에 넣을지 신경 써야 한다(「지금 묶음」 하나로 줄임).
- B. 변경 일지에서 골라 묶기. 따로 할 일이 없지만 일지는 문장 요약만 저장해서(`0002_change_journal.sql` 의 `statement_summary`) 전문 저장으로 바꿔야 하고, 시행착오 DDL 을 골라내는 일이 생긴다.
- C. 두 DB 구조를 비교해 만들기(스키마 비교). 빠뜨림이 없지만 PRD 6.13 의 별도 큰 프로젝트다. 다음 작업으로 둔다.
- 사용자는 A 를 고르고, SQL 편집기에서 직접 실행한 DDL 도 넣자고 했다(B 의 장점을 A 에 더함).

### 6.3 DDL 만드는 방식 **[설계자 결정 TE-3]**

- 고른 것: **원본 모델 + 편집 모델의 차이 → 문장 목록**. 편집을 켤 때 `TableInfo`(열·제약·인덱스·주석) 를 원본으로 복사해 두고, 표는 편집 모델을 고친다. 미리보기·실행·저장은 매번 두 모델의 차이에서 문장을 다시 만든다. 사용자가 한 칸을 고쳤다 되돌리면 문장도 사라진다.
- 버린 것: 편집 동작마다 문장을 쌓는 방식(명령 기록). 고쳤다 되돌린 칸이 문장으로 남고, 순서 의존이 꼬인다.
- 새 테이블은 원본이 빈 모델이다. 차이 = 전부 추가이므로 `CREATE TABLE` 하나로 모은다. 이때 `CreateTableDdl`(`src/Oranda.Core/Transfer/Copy/CreateTableDdl.cs`)의 열 표기(`TypeText`)·가상 열 표기를 재사용한다 **[구현: 재사용 범위]**. 단, `CreateTableDdl` 은 복사용이라 서버가 만든 이름을 건너뛰는 규칙(`IsSystemName`)이 있다. 새 테이블에서는 이름을 사용자가 정하므로 그 규칙에 걸리지 않게 한다.

## 7. 화면과 동작

### 7.1 편집 켜기·끄기 (기존 테이블)

- 객체 상세의 「열」「제약」「인덱스」「설명」 페이지 도구줄에 ✎ 편집 토글을 둔다. 대상은 TABLE 객체만이다(`ObjectDetailViewModel.CanReorderColumns` 판정과 같은 자리).
- 편집을 켜면 그때의 `TableInfo` 를 메타데이터에서 **새로 읽어**(캐시 무시) 원본으로 삼는다 **[설계자 결정 TE-4]**. 남이 그사이 바꾼 구조 위에 문장을 만들지 않게 하려는 것이다.
- 편집 모드는 탭 단위다. 「열」에서 고치고 「제약」 으로 가도 고친 내용은 유지되고, DDL 미리보기는 탭 전체(모든 페이지)의 차이를 보여 준다. 페이지 이름 옆에 바뀐 건수를 표시한다 **[구현: 표시 모양]**.
- 편집 중 다른 페이지(일반·통계 등)는 그대로 볼 수 있다. 「새로 고침」은 편집 중에는 「고친 내용을 버리고 새로 읽을까요?」를 묻는다.
- 편집을 끄거나 탭을 닫을 때 고친 내용이 있으면 버릴지 묻는다(4장 반목표).
- 실행이 성공하면 메타데이터 캐시를 무효화하고 상세를 다시 연 뒤 편집을 끈다. 열 순서 바꾸기의 `Applied` → `OpenAsync` 경로(`ObjectDetailView.axaml.cs:85-86`, `ColumnReorderViewModel.cs:337,349`)와 같다.
- 실행이 중간에 실패하면(앞 문장 성공, 뒤 문장 실패) 상세를 다시 읽고, 원본을 새 상태로 바꾼 뒤 **남은 편집을 다시 계산**해 아직 반영되지 않은 문장만 미리보기에 남긴다 **[설계자 결정 TE-5]**. 실패 메시지는 페이지 아래와 메시지 창에 보인다.
- 표 편집 컨트롤: 지금 `DetailTable`(`Shell/Controls/DetailTable.cs`)은 표시 전용이다. 편집 모드에서는 편집 가능한 표로 바꿔 보인다 **[구현: 새 컨트롤 또는 DetailTable 확장. 결과 그리드 편집(`ObjectDataView` 의 `EditToggle`)과 키 조작을 맞춘다]**.

### 7.2 열 페이지

칸: 이름, 형식, 길이(문자 형식은 길이, NUMBER 는 정밀도), 소수(NUMBER 만), NULL, 기본값, 가상 식, 주석. 지금 상세의 「#」 칸은 편집 중에도 원래 순서를 보여 준다.

- 형식은 목록에서 고르거나 직접 쓴다. 목록: VARCHAR2, NVARCHAR2, CHAR, NCHAR, NUMBER, DATE, TIMESTAMP, TIMESTAMP WITH TIME ZONE, CLOB, NCLOB, BLOB, RAW, LONG(목록에는 없음, 기존 열 표시만) **[구현: Tibero 목록 차이]**.
- 길이 기준(BYTE/CHAR): 기존 열은 원래 기준을 유지한다. 새 열은 기준을 쓰지 않아 세션 기본값을 따른다 **[설계자 결정 TE-6]**. 원본과 편집 모델을 비교할 때 기준 표기 차이로 거짓 MODIFY 가 나오지 않게 정규화한다(4장).
- 가상 식 칸에 값이 있으면 그 줄은 가상 열이다. 형식은 비워도 되고(서버가 정함), 길이·NULL·기본값 칸은 흐리게 둔다. 가상 식을 고치면 아래에 미리보기 줄이 나온다(7.6).
- 신원 열(`IsIdentity`)·숨김 열(`IsInvisible`)·도메인 열은 읽어서 보여 주되 첫판에서 그 속성은 고치지 않는다 **[설계자 결정 TE-7]**. 이름·주석은 고칠 수 있다.
- 열 지우기는 줄을 빨강으로 표시만 하고, 다시 누르면 되살린다. 실행할 때까지 아무것도 바뀌지 않는다.

### 7.3 제약 페이지 **[설계, 화면 ③]**

- 「＋ ▾」에서 PK·UK·FK·CHECK 를 고르면 새 줄이 생기고 이름이 규칙대로 채워진다. PK 는 이미 있으면 메뉴에서 흐리다.
- 열은 목록(이 테이블의 열, 편집 중 새 열 포함)에서 여러 개 고른다. FK 는 참조 테이블과 참조 키(PK·UK)를 고르고, 참조 키의 열 수에 맞춰 열을 고르게 한다. 삭제 규칙(없음·CASCADE·SET NULL)을 고른다.
- CHECK 는 조건 칸에 식을 쓴다. NOT NULL 은 열 페이지 NULL 칸이 맡고, 시스템 이름의 NOT NULL CHECK 는 이 페이지에 보이지 않게 한다(지금 상세와 같은지 확인) **[구현]**.
- 「사용」 체크를 끄면 `DISABLE CONSTRAINT`, 켜면 `ENABLE CONSTRAINT`. 이미 있는 제약의 열·조건 변경은 DROP + ADD 두 문장이다.
- 서버가 만든 이름(SYS_C…)의 제약을 지우거나 바꾸면 그 이름으로 문장을 만든다. 이 문장은 다른 DB 에서는 이름이 달라 실패하므로 미리보기와 묶음에 ⚠ 표시를 단다 **[설계자 결정 TE-8]**.
- 번호 `NN` 은 이 테이블의 같은 종류 제약 중 가장 큰 번호 + 1, 두 자리 **[구현: 서버 이름 길이 한도(30·128 바이트)를 넘으면 테이블 이름 쪽을 줄임]**.

### 7.4 인덱스 페이지 **[설계, 화면 ④]**

- 칸: 이름, 유일, 종류, 열(순서·ASC/DESC 포함), 테이블스페이스.
- 종류는 NORMAL 만 새로 만든다. 함수 기반·비트맵 인덱스는 보여 주되 지우기만 된다 **[설계자 결정 TE-9]**.
- PK·UK 제약이 만든 인덱스는 흐리게 두고 제약 페이지에서 고친다.
- 열 구성 변경은 DROP + CREATE 두 문장이다. 이름 변경은 `ALTER INDEX … RENAME TO`.

### 7.5 새 테이블 **[설계, 화면 ①]**

- 들어가는 길: 스키마 브라우저 소유자 노드와 「테이블」 폴더 노드의 오른쪽 클릭 「새 테이블…」. 소유자 노드는 지금 `schemaNodeSelected` 가 거짓이라(`SchemaBrowserViewModel.SavedFilters.cs:262`) 새 활성 조건 키가 필요하다 **[구현]**. 테이블 노드에는 「이 구조로 새 테이블…」.
- 탭 이름은 「✎ 새 테이블」. 위에 소유자(목록, 기본은 고른 노드의 소유자)·이름·주석 칸이 있다. 페이지는 열·제약·인덱스만 켜지고 나머지는 흐리다. 처음부터 편집 모드이며 편집 토글은 끌 수 없다.
- 미리보기는 `CREATE TABLE` (PK·UK·CHECK 는 안에, FK 는 뒤 `ALTER TABLE … ADD CONSTRAINT`), `COMMENT ON TABLE`, `COMMENT ON COLUMN …`, `CREATE INDEX …` 순서다.
- 이름 규칙의 `<테이블>` 은 이름 칸을 고치면 따라 바뀐다. 사용자가 직접 고친 제약 이름은 따라 바뀌지 않는다.
- 실행이 성공하면 같은 탭을 그 테이블의 객체 상세로 연다. 스키마 브라우저 캐시를 무효화해 새 테이블이 보이게 한다.
- 「이 구조로 새 테이블…」: 원본 테이블의 열(가상 열 포함)·주석·제약·인덱스를 복사해 채운다. 제약·인덱스 이름은 새 테이블 이름으로 규칙대로 다시 만든다. FK 는 같은 참조로 복사한다. 원본의 신원 열 속성은 가져오지 않는다(TE-7).
- 이 탭은 앱을 닫으면 사라진다. 작업 중 내용을 저장해 두는 기능은 첫판에 없다 **[설계자 결정 TE-10]**. 닫을 때 버릴지 묻는다.

### 7.6 가상 식 미리보기 **[설계, 화면 ⑤]**

- 가상 식을 고치고 칸을 벗어나면 `SELECT <식> FROM <테이블> WHERE ROWNUM <= 5`(식에 쓰인 열도 같이) 로 읽어 표 아래 한 줄로 보여 준다. 새 테이블은 데이터가 없으므로 미리보기 대신 `SELECT <식> FROM (SELECT CAST(NULL AS …) …)` 같은 문법 확인만 한다 **[구현: 문법 확인 방법. 서버로 파싱만 하는 방법이 있으면 그것]**.
- 식이 다른 새 열(아직 없는 열)을 쓰면 미리보기는 「실행 뒤에 확인」으로 표시하고 건너뛴다.
- 계산이 실패하면 오류 메시지를 그 줄에 보여 주고, 실행 전 검사에서 ✖ 가 된다.

### 7.7 DDL 미리보기와 아래 단추

- 페이지 아래 DDL 영역은 읽기 전용이고 문장 순서는 실제 실행 순서다(8.3). 복사할 수 있다. 「편집기로 열기」 메뉴로 SQL 편집기에 옮길 수 있다(옮긴 뒤 편집기에서 실행하면 그 DDL 은 SQL 편집기 출처로 묶음에 들어간다).
- 단추: 환경 표시(개발/테스트/운영 배지), 「묶음에 넣기 ▾」(지금 묶음 · 다른 묶음 · 새 묶음…), 「스크립트 저장…」(이 편집만 `.sql` 로), 「실행」.
- 개발·테스트 접속은 「실행」 이 기본 단추다. 운영 접속은 「의뢰용 스크립트 저장…」을 강조하고 「실행」은 보통 단추로 둔다 **[설계]**.
- 「실행」 성공 시 「지금 묶음」이 있으면 그 문장들이 자동으로 묶음에 들어간다(SQL 편집기와 같은 규칙, 9.3). 「묶음에 넣기」는 실행 없이 넣는다.

## 8. 바뀐 내용 → DDL (Core)

### 8.1 모듈

- Core `Oranda.Core.Schema.TableEdit` (이름은 **[구현]**): 편집 모델(`TableDraft`: 열·제약·인덱스·주석 목록, 각 줄의 원본 키), 차이 계산(`TableDraftDiff`), 문장 만들기(`TableEditScriptBuilder`). 방언 인터페이스 `ITableEditDialect` 를 Oracle·Tibero 가 구현한다(열 순서 바꾸기의 `IColumnReorderScripts` 구성과 같은 꼴).
- 차이 계산은 원본 줄과 편집 줄을 **줄 키**(원본 이름이 아니라 편집을 켤 때 붙인 고유 키)로 맞춘다. 이름 바꾸기와 지우고 새로 넣기를 구분하기 위해서다.
- 결과는 `SqlStatement` 목록(`Kind = Ddl`)과 각 문장의 설명(어느 줄에서 나왔는지, ⚠ 표시)이다.

### 8.2 문장 꼴 (Oracle 기준)

| 바뀐 것 | 문장 |
|---|---|
| 열 추가 | `ALTER TABLE o.t ADD (c type [DEFAULT x] [NOT NULL])` · 가상 열 `ADD (c [type] AS (expr) VIRTUAL)` |
| 열 지우기 | `ALTER TABLE o.t DROP COLUMN c` |
| 열 이름 | `ALTER TABLE o.t RENAME COLUMN a TO b` |
| 형식·길이·NULL·기본값 | `ALTER TABLE o.t MODIFY (c type [DEFAULT x] [NULL\|NOT NULL])` — 바뀐 속성만 쓴다 |
| 기본값 없애기 | `MODIFY (c DEFAULT NULL)` |
| 가상 식 변경 | `MODIFY (c AS (expr))` **[구현: Oracle 허용 여부 실측, 안 되면 DROP + ADD 와 ⚠]** |
| 주석 | `COMMENT ON TABLE o.t IS '…'` · `COMMENT ON COLUMN o.t.c IS '…'` (지우기는 `IS ''`) |
| 제약 추가 | `ALTER TABLE o.t ADD CONSTRAINT n PRIMARY KEY (…)` / `UNIQUE` / `FOREIGN KEY (…) REFERENCES o2.t2 (…) [ON DELETE …]` / `CHECK (…)` |
| 제약 지우기·사용 | `DROP CONSTRAINT n` · `ENABLE CONSTRAINT n` · `DISABLE CONSTRAINT n` |
| 인덱스 | `CREATE [UNIQUE] INDEX o.n ON o.t (c1 [DESC], …) [TABLESPACE ts]` · `DROP INDEX o.n` · `ALTER INDEX o.n RENAME TO m` |

- 이름은 늘 소유자를 붙여 쓴다(`SAMPLE.ORDERS`). 따옴표는 이름이 대문자 규칙을 벗어날 때만 붙인다(기존 `CreateTableDdl` 규칙 재사용) **[구현]**.
- 같은 열의 여러 속성 변경은 `MODIFY` 한 문장으로 모은다. 여러 열의 MODIFY 를 한 문장으로 모으지는 않는다(실패 지점을 줄 단위로 보이게) **[설계자 결정 TE-11]**.

### 8.3 문장 순서 **[설계자 결정 TE-12]**

1. 지울 FK(이 테이블의 것) → 지울·바꿀 제약 → 지울·바꿀 인덱스
2. 열 이름 바꾸기
3. 열 MODIFY
4. 열 추가(일반 열 먼저, 가상 열 나중)
5. 열 지우기
6. 제약 추가(PK·UK → CHECK → FK) · ENABLE/DISABLE
7. 인덱스 만들기 · 이름 바꾸기
8. 주석

이유: 지울 열을 참조하는 제약·인덱스가 먼저 사라져야 하고, 새 제약은 새 열과 바뀐 형식 위에서 만든다. 가상 열은 그 식이 쓰는 새 열 뒤에 온다. 열 지우기를 열 추가 뒤에 둬서, 같은 이름으로 지우고 다시 넣는 경우가 문장 순서로 막히지 않게 한다 **[구현: 같은 이름 지우고 넣기는 지우기를 먼저 해야 함 — 이 경우만 예외 처리]**.

### 8.4 거짓 차이 막기 (4장 반목표)

비교 전에 원본과 편집 모델을 같은 규칙으로 정규화한다: 형식 이름 대소문자, `NUMBER` 의 기본 정밀도, 문자 길이 기준, 기본값 앞뒤 공백·줄바꿈, 가상 식의 서버 표기(서버는 식을 따옴표 붙여 대문자로 돌려준다), 주석 `NULL` 과 빈 문자열. 「편집을 켜고 아무것도 안 고치면 문장 0개」를 Oracle·Tibero 실측 테이블 여러 개로 시험한다(14장).

## 9. 반영 묶음

### 9.1 저장 (`oranda.db`, 마이그레이션 `0006_change_bundle.sql`) **[설계자 결정 TE-13]**

- `change_bundle`: id, 이름, 만든 때, 고친 때, DBMS 종류(Oracle/Tibero), 대상 소유자 목록(하나 이상, TE-24), 「지금 묶음」 여부(하나만 참).
- `change_bundle_item`: id, 묶음 id, 순서, 문장 전문, 출처(테이블 편집 · SQL 편집기 · 직접 넣음), 대상 소유자·객체 이름, 체크 여부, 넣은 때, 문장 해시(공백 정규화), ⚠ 표시(TE-8 등).
- `change_bundle_run`: 항목 id, 환경(개발·테스트·운영), 접속 이름, 실행한 때, 성공 여부. 화면의 개발·테스트·운영 칸은 환경별 마지막 성공 날짜다.
- 묶음은 이 PC 에만 있다. 다른 PC 와 나누기는 첫판에 없다(스크립트 파일로 나눈다).

### 9.2 창 **[설계, 화면 ②]**

- 아래 도구 창, 변경 일지 옆(`[OrandaToolPanel(..., DockLocation.Bottom, Order = 46)]`, 변경 일지는 45). 메뉴 「도구 > 반영 묶음」.
- 제목줄: 「지금 묶음」 고르기(목록), ＋ 새 묶음 · 이름 바꾸기 · 지우기(확인).
- 도구줄: ↑ ↓(순서), －(지우기), 「실행…」, 「의뢰용 스크립트 저장…」, 오른쪽에 대상 DBMS.
- 표: 체크, #, 문장(한 줄 요약, 두 번 누르면 전문 보기·편집기로), 출처, 개발, 테스트, 운영. 체크 해제 줄은 흐리게.
- 문장 전문은 묶음 창에서 고칠 수 있다(오타 고치기). 고치면 그 문장의 실행 표시는 지운다 **[설계자 결정 TE-14]**.
- 「실행…」은 접속을 고르는 창을 띄운다(지금 열린 접속 목록, 기본은 묶음 DBMS 와 같은 테스트 접속). 시안의 「테스트에 실행…」을 이렇게 넓힌다 **[설계자 결정 TE-15]**. 체크한 문장을 순서대로 `ExecuteScriptAsync(..., ScriptErrorMode.Stop)` 로 보내고, 성공한 문장마다 실행 표시를 남긴다. 운영 접속이면 SAFE-03 확인을 한 번 받는다(5장).
- 묶음 실행 전에도 실행 전 검사(10장)를 문장마다 한다. 묶음 문장은 편집 모델이 없으므로 문장을 해석할 수 있는 것(ALTER MODIFY 길이·NOT NULL, ADD CONSTRAINT 등)만 검사하고, 나머지는 검사 없이 보낸다 **[구현: 해석 범위]**.

### 9.3 자동으로 넣기

- 실행 엔진이 내는 `StatementExecuted`(`src/Oranda.Core/Events/Events.cs:23`)를 받아, 다음을 모두 만족하면 「지금 묶음」 끝에 넣는다:
  - 「지금 묶음」이 있다.
  - `Statement.Kind == Ddl` 이고 성공했다.
  - 출처(`Options.Source`)가 SQL 편집기·스크립트 실행 또는 테이블 편집기다. 묶음 실행·열 순서 바꾸기·데이터 복사·에이전트·모니터는 넣지 않는다 **[설계자 결정 TE-16]**. 묶음 실행을 구분하려면 `HistorySource` 에 값을 더한다(`TableEditor`, `ChangeBundle`) **[구현]**.
  - 접속 DBMS 가 묶음 DBMS 와 같다. 다르면 넣지 않고 메시지 창에 한 줄 알린다. 빈 묶음은 첫 문장의 DBMS 를 따른다.
  - 문장이 바꾸는 객체의 소유자(분류기 `ChangeTarget`, 소유자를 안 쓴 문장은 그 세션의 현재 스키마)가 묶음의 대상 소유자 목록에 있다. 없으면 넣지 않는다(메시지 없음). 새 묶음을 만들 때 대상 소유자는 지금 접속의 현재 스키마로 채우고 사용자가 더하거나 뺀다 **[설계자 결정 TE-24]**.
  - 묶음에 넣는 문장은 소유자를 붙인 꼴로 바꿔 저장한다(소유자 없이 쓴 DDL 에 현재 스키마를 붙임). 의뢰 스크립트가 실행 계정과 상관없이 같은 객체를 바꾸게 하려는 것이다 **[구현: 렉서로 대상 이름만 고침, 못 고치면 원문 그대로 넣고 ⚠]**.
- 같은 묶음에 해시가 같은 문장이 이미 있으면 새로 넣지 않고 그 항목에 실행 표시만 남긴다. 그래서 개발에서 실행해 묶음에 들어간 문장을 테스트 접속 SQL 편집기에서 다시 실행해도 겹치지 않고 「테스트 ✔」가 붙는다.
- 넣으면 묶음 창 제목에 건수가 잠깐 표시된다(창을 열지는 않는다) **[구현]**.
- 어떤 DDL 을 넣을지(GRANT·TRUNCATE·DROP TABLE 등 `Ddl` 로 분류되는 모든 것)는 분류기(`StatementClassifier.cs:53`) 결과를 그대로 따른다. 빼고 싶은 건 사용자가 체크를 끈다.

### 9.4 의뢰용 스크립트 저장

- 체크한 문장만 화면 순서대로 `.sql` 한 파일에 쓴다. DDL 만 담는다(묶음에는 DDL 만 들어가므로 따로 거르지 않지만, 혹시 다른 종류가 있으면 저장을 막는다).
- 머리 주석: 묶음 이름, 만든 날짜, 대상 DBMS, 문장 수. 접속 이름·호스트는 넣지 않는다.
- 문장 끝: 일반 DDL 은 `;`, PL/SQL 블록은 줄 `/`. SQL*Plus 와 Tibero tbSQL 에서 그대로 돌아가는 꼴이다 **[구현: tbSQL 실측]**.
- 인코딩 UTF-8(BOM 없음), 줄바꿈은 OS 기본 **[설계자 결정 TE-17]**.
- 저장 창에 「소유자 바꾸기」 칸을 둔다: 묶음의 대상 소유자마다 저장할 이름을 적을 수 있고(기본은 같은 이름), 바꾸면 문장 안의 그 소유자 한정 이름(`SAMPLE.` 뒤에 이름이 오는 꼴)만 렉서로 바꿔 쓴다. 문자열 리터럴·주석 안은 건드리지 않는다. 테스트·운영의 스키마 이름이 개발과 다른 경우에 쓴다 **[설계자 결정 TE-22]**. 묶음 「실행…」 창에도 같은 칸을 둔다.
- 테이블스페이스는 문장에 쓰지 않아 실행 계정의 기본값을 따른다. 그래서 머리 주석에 「테이블스페이스를 쓰지 않은 문장은 실행 계정의 기본 테이블스페이스에 만들어진다」 한 줄을 넣는다. 특정 테이블스페이스가 필요하면 편집기에서 그 칸을 열어 명시한다 **[설계자 결정 TE-22]**.
- 편집기의 「스크립트 저장…」도 같은 형식이다(묶음 이름 대신 테이블 이름).

## 10. 실행 전 검사 **[사용자: ✖ 막고 ⚠ 알림, 2026-11-17]**, **[설계, 화면 ⑤]**

「실행」·「묶음에 넣기」·묶음 「실행…」 앞에 돈다. 읽기만 한다. 제목줄에 테이블과 대략 행 수(통계 `NUM_ROWS`, 없으면 「알 수 없음」), 환경 배지.

| 판정 | 조건 | 표시 |
|---|---|---|
| ✖ | 문자 길이·숫자 정밀도를 줄이는데 넘치는 행이 있다(`MAX(LENGTH)`, `COUNT(*) WHERE …`) | 「넘치는 행 N건」 + 「그 행 보기」(SQL 편집기에 SELECT 열기) |
| ✖ | 형식 변경이 데이터가 있으면 안 되는 변경이다(예: VARCHAR2 → NUMBER, 데이터 있는 열) | 이유 |
| ✖ | NOT NULL 추가인데 NULL 행이 있다 | 「NULL 행 N건」 **[설계자 결정 TE-18: 시안 ⑤ 는 ⚠ 였지만, 실패가 확실하므로 사용자 규칙대로 ✖]** |
| ✖ | PK·UK 추가인데 중복 키가 있다 / FK 추가인데 짝 없는 행이 있다 / CHECK 추가인데 어기는 행이 있다 | 건수 + 「그 행 보기」 |
| ✖ | 가상 식 계산이 실패한다 | 서버 오류 메시지 |
| ✖ | 이름이 이미 있다(열·제약·인덱스) | 이름 |
| ⚠ | 운영 접속이고 행이 많다(기준 **[구현: 설정값, 기본 100만 행]**) 이며 MODIFY·NOT NULL·제약 추가·인덱스 만들기가 있다 | 「오래 잠글 수 있음. 의뢰용 스크립트 저장을 권함」 |
| ⚠ | DROP COLUMN·DROP CONSTRAINT·DROP INDEX | 데이터를 되돌릴 수 없음(되돌리기 지점으로도) · 이 열을 쓰는 뷰·트리거·PL/SQL 목록(의존 정보) |
| ⚠ | 서버 이름(SYS_C…) 제약을 다룬다 | 다른 DB 에서 실패 (TE-8) |
| ⚠ | 검사 질의가 시간 제한(기본 10초 **[구현: 설정값]**)을 넘었다 | 「확인 못 함」 |
| ✔ | 위에 걸리지 않음 | 항목별 한 줄 |

- ✖ 가 하나라도 있으면 실행과 묶음 넣기를 막는다. 「의뢰용 스크립트 저장」도 막을지: 막지 않는다. 운영과 개발의 데이터가 다르므로, 개발 데이터로 실패해도 스크립트는 저장할 수 있게 한다 **[설계자 결정 TE-19]**.
- ⚠ 만 있으면 확인 창에 보이고 「그래도 실행」 할 수 있다. 개발 접속에서 ⚠ 만 있으면 창을 띄우지 않고 미리보기 아래 줄에만 보인다(D-065 개발 접속 확인 생략과 맞춤) **[설계자 결정 TE-20]**.
- 운영 접속은 SAFE-03 확인 창과 검사 창이 둘 다 뜨지 않게, 검사 결과를 SAFE-03 확인 창 안에 넣어 한 번만 묻는다 **[구현: `IExecutionInteraction` 확장 방식]**.

## 11. 실행과 결과

- 실행은 `IExecutionService.ExecuteScriptAsync(…, ScriptErrorMode.Stop, new ExecutionOptions { Source = HistorySource.TableEditor })`. 실행 이력·변경 일지(DDL 앞 이전 DDL 저장)는 지금처럼 남는다.
- 변경 일지가 DDL 앞 이전 구조를 남기므로, 테이블 편집 실행도 변경 일지에서 「이전 DDL」로 볼 수 있다. 별도 되돌리기 기능은 첫판에 없다.
- 성공·실패 후 상세 다시 읽기는 7.1.

## 12. Tibero

목표는 첫 배포부터 Oracle 과 같은 기능 수준이다. Tibero 만 늦게 내거나 기능 끄기로 숨기지 않는다. 방언(`ITableEditDialect` Tibero 구현)과 실측으로 다룬다. 실측은 방언 모양을 바꾸므로 계획의 맨 앞(Core 차이 계산과 나란히)에 둔다. win30 이 실측한다(15장).

실측 목록(결과는 이 장에 적어 넣는다):

1. 가상 열 `ADD (c AS (expr) VIRTUAL)` 과 가상 식 변경.
2. `RENAME COLUMN`, `ALTER INDEX … RENAME TO`.
3. `MODIFY` 로 길이 줄이기 실패 시 오류와 `DbErrorKind` 분류.
4. `ENABLE/DISABLE CONSTRAINT`, FK `ON DELETE SET NULL`.
5. `CREATE INDEX … (c DESC)`.
6. 제약·인덱스 이름 길이 한도.
7. 서버가 돌려주는 가상 식·기본값 표기(거짓 차이 정규화용, 8.4).
8. 형식 목록 차이(예: NVARCHAR2·TIMESTAMP WITH TIME ZONE 지원).
9. `/` 줄과 `;` 를 쓴 의뢰 스크립트가 tbSQL 에서 그대로 도는지.
10. DDL 암묵 커밋 동작(Oracle 과 같은지).

알려진 차이: 숨김 열 없음(`TiberoColumnReorderScripts.cs:31` `InvisibleNotSupported`), 휴지통 꺼짐이 기본이라 DROP 이 영구(`TiberoColumnReorderScripts.cs:87-88`) — DROP 계열 ⚠ 문구에 반영한다. 클러스터 테이블 판정 없음.

## 13. 기존 기능과의 관계

- **열 순서 바꾸기**: 기존 열 순서는 그대로 그 창이 맡는다. 편집 모드 열 페이지 도구줄에 「열 순서 바꾸기…」를 그대로 둔다. 편집 중 고친 내용이 있으면 그 창을 열기 전에 실행하거나 버리라고 묻는다.
- **데이터 복사**: `CreateTableDdl` 을 공유한다. 공유 부분을 고치면 데이터 복사 시험도 돌린다.
- **변경 일지**: 바꾸지 않는다. 반영 묶음은 별도 표다(6.2 방식 B 를 버린 이유).
- **SQL 편집기**: 실행 경로는 바꾸지 않는다. 묶음 자동 넣기는 이벤트 구독으로만 붙는다.
- **기능 끄기**: `FeatureCatalog` 에 「테이블 편집」·「반영 묶음」 기능을 더해 끌 수 있게 한다 **[구현]**.

## 14. 시험

- Core 단위: 차이 → 문장(8.2 표의 모든 줄, 순서 8.3, 같은 이름 지우고 넣기, 고쳤다 되돌리기 = 0문장), 거짓 차이 정규화(8.4), 이름 규칙(길이 한도 포함), 의뢰 스크립트 형식(9.4), 자동 넣기 조건(9.3, 출처·DBMS·해시 중복).

- App: 편집 켜기·끄기·버림 확인, 페이지 이동 유지, 실행 후 다시 읽기, 실패 후 남은 문장 다시 계산(TE-5), 새 테이블 탭 → 상세 전환, 묶음 창 순서·체크·실행 표시.
- 매뉴얼 그림: `Manual*Screens` 시험으로 편집 모드 열 페이지·새 테이블·묶음 창·검사 창(Windows 렌더는 win30).

## 17. 빌더 점검 결과 (2026-11-17)

빌더 점검 질문 다섯 개를 이렇게 정리했다. 사용자는 1·2·4번을 「알아서 진행해」로 설계자에게 맡겼다.

1. 환경마다 소유자 이름·실행 계정이 다를 수 있음 → TE-22(저장·실행 때 소유자 바꾸기, 테이블스페이스 생략 알림).
2. 환경마다 DBMS 가 다를 수 있음 → TE-23(같은 DBMS 로 보고 섞인 묶음은 범위 밖).
3. 운영 확인 한 번을 무엇으로 → TE-21(`PreConfirmed` 문장별 실행).
4. 「지금 묶음」 범위 → TE-24(묶음별 대상 소유자).
5. Tibero 첫 배포 포함 → 포함(2장, 12장), 실측을 계획 맨 앞에.
