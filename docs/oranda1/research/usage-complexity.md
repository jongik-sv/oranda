# 사용 복잡도 조사 — 어디서 복잡해지고 무엇을 줄일까

> 작성 2026-10-25 · 기준 커밋 `413a33d` (dev-jji-win144) · 읽기 전용 조사(코드 변경 없음)
> 목적: 기능을 계속 붙이면서 사용자가 느끼는 복잡도가 어디서 생기는지 찾고, 줄일 안과 Task 후보를 낸다. 메모리 절감은 목표가 아니다.
> 표기: 근거는 `파일:줄`(경로는 저장소 뿌리 기준). 「추측」은 코드로 확인하지 못한 판단이다.

## 0. 한눈에

- **Role 로 줄어드는 몫은 3분의 1이 한계다.** 「모든 기능 켬」의 메뉴 항목은 274개다. 그중 176개(64 %)가 공통 명령이라 어떤 Role 을 골라도 남는다. 가장 작은 R6 도 184개(-33 %)이고, R5 DBA 는 256개(-7 %)라 거의 줄지 않는다.
- **가장 큰 메뉴는 Role 과 상관없는 공통 메뉴다.** 「편집」 53개(Role 을 골라도 48개), 「결과」 37개, 「파일」 32개는 하위 메뉴 없이 한 줄로 늘어서 있다. 15개를 넘는 메뉴가 「모든 기능」에서 8개, 가장 단순한 Role 에서도 5개다. 그리드 오른쪽 클릭 메뉴는 항목이 37개다.
- **이름과 자리가 겹친다.** 「실행 취소」(Undo)와 「실행 취소(서버 중단)」가 함께 있다. 보기 메뉴에는 같은 도구 창을 여는 명령이 2번씩 나오는 경우가 7개 있다. 템플릿은 3곳, 레이아웃 초기화는 2곳에 있다. 예상·실제 계획은 SQL·튜닝 메뉴 두 곳에 있다. 같은 일을 하는 내보내기 대화상자가 2개 있다. 세션 끊기는 모니터마다 이름이 다르다.
- **Role 기능 자체도 부담이다.** 기본값은 「모든 기능 켬」이다. 입구는 도구 메뉴와, 문서가 없을 때만 보이는 시작 화면 한 줄뿐이다. 「기능」 탭의 입력 칸은 33개(라디오 2, Role 6, 기능 25)로, 나머지 설정 탭 8개를 합친 수(약 39개)와 비슷하다. 「Role 로 고르기」로 바꾸면 Role 이 하나도 체크되지 않은 상태로 시작해 25개 기능이 모두 꺼져 보인다.
- 권장 순서: ① 공통 메뉴(편집·결과·파일·그리드 오른쪽 클릭)를 하위 메뉴로 묶고 중복·충돌하는 이름을 정리한다. 모든 사용자가 효과를 본다. ② Role 고르기를 「주 업무 하나 + 덧붙임 2개」로 줄이고, 기능 25개는 「고급」으로 접고, 새 설치 시작 화면에서 한 번 묻는다. ③ R6 내보내기 알림 결함(TSK-07-09)처럼 주 작업 흐름을 끊는 결함부터 고친다.

주:
1. 메뉴 항목 = 명령이 놓인 메뉴 자리 수(`menu:` 배치) + 오른쪽 클릭에만 있어 「결과」·「데이터베이스」 메뉴로 옮겨 싣는 명령(`src/Oranda.App/Shell/Menus/MenuModel.cs:161,204-221`) + 보기 > 도구 창 토글(`MenuModel.cs:227-230,334`). 한 명령이 두 메뉴에 있으면 2로 센다(예상 계획 등). 구분선과 「최근 파일」처럼 열 때 채우는 줄(`MenuItemSources`)은 뺐다.
2. SQL 탭이 활성일 때 `When` 규칙(`src/Oranda.App/Shell/Menus/MenuVisibility.cs:30-41`)으로 보이는 명령 항목이다. 보기 > 도구 창 토글은 뺐다. 모니터·Lock 모니터·MyBatis·PL/SQL 탭 전용 항목은 이 상태에서 숨는다.
3. 최상위 메뉴 > 하위 메뉴 > 항목. 하위 메뉴는 최근 파일·최근 작업 공간·테마·도구 창·스크립트 오류 시·다시 실행(통계)·스크립트(튜닝)·단축키 프리셋이다. **깊이는 문제가 아니다. 문제는 너비다.**
4. 오른쪽 클릭 표면 전체 합(그리드·편집기·스키마 외에 계획 2, 세션 모니터 8, Lock 모니터 6, MyBatis 편집기·펼친 SQL·문장 목록 9, 문서 탭 1).
5. 등록 도구 창(`Tool` 종류, 개발 빌드 전용 확장 시험 창 제외) / 기본 배치에 들어가는 수(`src/Oranda.App/Shell/Layout/LayoutPlanner.cs:30-45`: 왼쪽·아래 전부 + 오른쪽 바인드·템플릿) / SQL 탭에서 실제로 보이는 수(MyBatis 창 2개는 MyBatis 문서에서만 보임, `src/Oranda.App/Shell/Docking/DockWorkspace.ScopedTools.cs:33-57`).
6. 보기 메뉴에는 도구 창 토글이 포함되어 있다(모든 기능 15개).

### 1.2 센 방법과 검증

- `src/**/*.cs` 의 `[OrandaCommand]` 282개와 `[OrandaToolPanel]` 33개를 파서로 읽었다(id·Placements·When·네임스페이스, 상수 id 풀이 포함). 거기에 `FeatureCatalog.FeatureFor`(`src/Oranda.Core/Features/FeatureCatalog.cs`: id 덮어쓰기 → 형 이름 덮어쓰기 → 네임스페이스 가장 긴 접두), `FeatureCatalog.Resolve`(합집합·조회 전용 쓰기 기능 끔·Requires), `MenuModelBuilder.BuildMenuBar`(`MenuModel.cs:163-250`: navigate→편집, 오른쪽 클릭 옮겨 싣기, 기능에 매인 최상위 메뉴 숨김 `:151-155`) 규칙을 그대로 옮겨 계산했다. 명령 제목은 `src/Oranda.App/Shell/Resources/CommandTitles.json` 에서 읽었다.
- 검증: 「설정 없음」은 TSK-07-08 기준선(명령 282, 최상위 메뉴 11, 상태 칸 10)과 같다(`docs/oranda1/itest/TSK-07-08.md:43`). 상태 칸 수 R1 9·R3 10·R6 7 은 TSK-07-07 측정값(`docs/oranda1/itest/TSK-07-07.md:81`)과 같다.
- 한계: 앱을 띄워 센 숫자가 아니다. 메뉴 항목 수는 위 규칙으로 계산한 값이다. 정확한 값이 필요하면 시험 도우미 `RoleApp.Capture()`(`tests/Oranda.App.Tests/Integration/Roles/RoleApp.cs:268`)로 같은 표를 뽑을 수 있다(이번에는 저장소에 파일을 쓰지 않으려고 하지 않았다).

### 1.3 숫자가 말하는 것

- **공통이 64 %다.** 공통만(Role 0개) 176 / 모든 기능 274. 기능 꼬리표가 붙은 항목은 98개뿐이다. Role 을 아무리 잘게 나눠도 메뉴는 3분의 1 이상 줄지 않는다.
- **R5 DBA 는 25개 중 20개 기능을 켠다.** R1 의 기능 10개는 모두 R5 에 들어 있다(R1 ⊂ R5). DBA 에게 Role 은 거의 효과가 없다.
- **R1·R2·R3 은 서로 3~5개 기능만 다르다.** R1 과 R2 는 9/14 개를 공유하고, R1 과 R3 은 7/12 개를 공유한다. R4 와 R5 는 14/22 개를 공유한다. 사용자가 고르는 단위로는 6개가 지나치게 잘다(3장).
- R1·R2·R3 의 「튜닝」 최상위 메뉴는 항목 7개 가운데 2개(예상·실제 계획)가 SQL 메뉴와 겹친다. 고유 항목 5개 때문에 최상위 메뉴 하나가 생긴다.

## 3. Role 기능 단순화 안

### 3.1 지금의 부담 정리

1. **입구가 숨어 있다**(F1). 첫 실행에 묻지 않고(D-011), 시작 화면 링크는 문서가 없을 때만 보인다. 대부분의 사용자는 「모든 기능」으로 남을 것이다(추측).
2. **고르는 단위가 잘다**(1.3). R1·R2·R3 은 3~5개만 다르고 R1 ⊂ R5 다. 사용자는 「내가 PL/SQL 개발자인가 SQL 개발자인가」를 정하기 어렵다. 실제로 갈리는 질문은 「PL/SQL 패키지를 고치나」, 「MyBatis 매퍼를 쓰나」 두 가지다.
3. **화면이 크다**(E1·H2). 기능 25개가 기본으로 펼쳐져 있다.
4. **함정 상태가 있다**(H1). 라디오 → Role 0개 → 모두 꺼져 보임.
5. **효과가 한정적이다**(1.3). Role 로 줄어드는 것은 최대 33 %다. 큰 메뉴(편집·결과·파일)는 그대로다. 그래서 Role 만으로는 「복잡하다」는 느낌이 크게 줄지 않는다. 공통 메뉴 정리(5장 1·2번)를 같이 해야 한다.

## 4. 주 작업 흐름별 걸리는 곳

클릭 수는 마우스 기준이다(단축키를 쓰면 준다). 「화면」은 새로 뜨는 창·대화상자 수다.

### 4.1 R1 SQL 개발자 — 접속 → SQL 작성 → 실행 → 결과 보기·내보내기

| 단계 | 처음 쓰는 사람 | 클릭 | 화면 |
|---|---|---|---|
| 접속 | 시작 화면 「접속 관리자」(목록의 4번째 줄) → 「새 접속」 → 이름·호스트·서비스·사용자·비밀번호 5칸 입력(포트 1521 기본, `ProfileEditorViewModel.cs:215`) → 「접속」 → 창 닫힘 | 3 + 5칸 | 접속 관리자 1 |
| SQL 탭 | 시작 화면이 그대로 남는다 → 「새 SQL 편집기」(추측: 접속 뒤 편집기가 자동으로 열리지 않는다. `SessionOpened` 를 듣는 곳 중 편집기를 여는 곳이 없다) | 1 | – |
| 실행 | 입력 → 툴바 실행 또는 Ctrl+Enter | 1 | – |
| 내보내기 | 결과 우클릭(37개 메뉴) → 「Excel 로 내보내기…」 → 범위 고르고 확인 → 저장 위치 대화상자에서 저장 | 4 | 대화상자 2 |
| **합** | | **약 9 + 5칸** | **3** |

다시 쓰는 사람은 탭이 복원되고(`AppSettings.cs:209`), 접속이 없는 탭에서도 실행이 눌린다(`tabConnectionMissing`, `ExecutionCommands.cs:246`, 추측: 실행할 때 다시 접속을 묻는다). 접속 2 + 실행 1 + 내보내기 4 = 약 7클릭.

걸리는 곳:
- 접속이 없으면 실행이 회색이다. 시작 화면 첫 줄이 「새 SQL 편집기」라서, 접속 전에 탭부터 여는 길로 이끈다(`StartPage.cs:27-37`). 「새 SQL 편집기」와 「새 작업 공간」 중 무엇을 눌러야 하는지 설명이 없다(C4).
- 결과 우클릭 37개 중 내보내기가 「내보내기」와 「Excel 로 내보내기…」 두 개다(B3). 「복사」 묶음 7개(TSV·머리글·행·CSV·INSERT·IN 목록)가 앞에 있다(A3).
- 아래 탭 7개 중 결과·메시지·DBMS 출력이 자리를 다툰다(F2).

### 4.2 R2 PL/SQL 개발자 — 접속 → 패키지 열기 → 고치기 → 컴파일 → 오류 → 실행

| 단계 | 조작 | 클릭 |
|---|---|---|
| 열기 | 스키마 브라우저(왼쪽)에서 패키지 찾기(필터 입력 또는 트리 펼침 2~4) → 우클릭 「PL/SQL 소스 열기」 | 4~6 |
| 컴파일 | F5, 또는 편집기 안 「컴파일(저장)」 단추(`PlsqlEditorView.axaml:13`) | 1 |
| 오류 | 아래 「컴파일 오류」 탭(7탭 중 하나)에서 줄 더블클릭 | 1~2 |
| 실행 | Ctrl+Enter → 실행 대화상자 → 인자 입력 → 실행 | 2+ |

걸리는 곳:
- **컴파일·실행 대화상자·명세/본문 전환·서버와 차이가 주 메뉴에 없다**(B6). 실행 대화상자는 단축키(Ctrl+Enter)와 스키마 오른쪽 클릭으로만 연다. 메뉴로 기능을 찾는 사람은 못 찾는다.
- F5 가 SQL 탭에서는 「스크립트 실행」이고 PL/SQL 탭에서는 「컴파일(서버에 씀)」이다(G2).
- 「PL/SQL 작업 공간」과 SQL 「작업 공간」이 따로 있다(C4).

### 4.3 R3 MyBatis 개발자 — 매퍼 열기 → 문장 고르기 → 값 넣고 실행 → 조합 검사 → 저장

| 단계 | 조작 | 클릭 |
|---|---|---|
| 열기 | 파일 > 매퍼 폴더 열기… → 폴더 고르기 | 3 |
| 문장 | 왼쪽 「매퍼 쿼리」 창에서 문장 | 1 |
| 실행 | 바인드 창에 시나리오 값 → **F9**(Windows) 또는 MyBatis 툴바 실행 | 1 |
| 검사·저장 | MyBatis 툴바 「조합 검사」 → 「xml 에 저장」 → 차이 확인 창 | 3 |

걸리는 곳:
- **SQL 탭은 Ctrl+Enter 로, MyBatis 탭은 F9 로 실행한다**(G3). 같은 사람이 두 탭을 오가며 쓴다.
- 툴바가 2줄 몫이다: 주 툴바 14 + MyBatis 툴바 7. 저장도 3가지다: 「저장」·「xml 에 저장」·「작업 공간 저장」.
- MyBatis 명령 8개가 SQL 탭 메뉴에도 보인다(F4). 저장할 때마다 차이 확인 창이 뜬다(F3).

### 4.4 R4 DB 튜너 — 느린 SQL 찾기 → 계획 → 통계·커서 → 보고서

| 단계 | 조작 | 클릭 |
|---|---|---|
| 찾기 | 튜닝 > SQL 모니터(Top SQL) 또는 툴바 → 목록에서 SQL 고르기 | 2~3 |
| 계획 | 튜닝 > 선택 SQL 실제 계획(모니터 탭이 활성일 때만 메뉴에 나타남) 또는 SQL 탭에서 Ctrl+E / Ctrl+Shift+E | 1~2 |
| 통계·커서 | 계획 창의 표 통계·자식 커서 단추(`src/Oranda.App/Features/ExecutionPlan/PlanViewModel.Boost.cs:133-137`) | 1 |
| ASH·AWR | 막혀 있으면 → 접속 관리자 > 프로필 > 고급 설정 펼치기 > 팩 선언 > 저장 → 다시 접속 | 6+ |
| 보고서 | 튜닝 > 튜닝 보고서 만들기… → 저장 | 2 |

걸리는 곳:
- 팩 선언이 깊은 곳에 있다(E3). 기능 탭 안내에서 그리로 가는 길이 없다.
- 튜닝 메뉴 24개(SQL 탭에서 21개)는 용어가 영어 위주다(D1). 예상·실제 계획이 SQL 메뉴와 겹친다(B2).
- 보고서 저장 완료 알림이 R4 에서 보이지 않는다(D-1, gridEdit 가 꺼져 있음).

### 4.5 R5 운영 DBA — 세션·Lock 장애 대응

| 단계 | 조작 | 클릭 |
|---|---|---|
| 열기 | 툴바 「세션 모니터」 또는 모니터 > Lock 모니터 | 1~2 |

걸리는 곳:
- 같은 일의 이름이 화면마다 다르다(C2).
- 모니터 메뉴 21개 중 19개가 해당 탭이 활성일 때만 보인다(G1).
- R5 는 기능 25개 중 20개를 켜므로 Role 을 골라도 메뉴가 7 %만 준다(1.3).

### 4.6 R6 조회 전용 — 접속 → 조회 → 내보내기

흐름은 R1 과 같다(약 9클릭).
걸리는 곳:

- 편집 메뉴 48개·결과 메뉴 25개는 그대로다(A1·A2).
