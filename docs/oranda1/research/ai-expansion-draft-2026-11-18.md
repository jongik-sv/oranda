# AI 적용 확대와 모델 나눠 쓰기 — 시안

- 날짜: 2026-11-18
- 상태: 시안(WBS 에 올리기 전). 1·2순위를 구현하고, 3순위는 나중에 다시 정리한다.
- 질문: 「튜닝에만 쓰던 AI 를 다른 기능에도 쓰고, 간단한 일은 무료 로컬·가벼운 모델로, 복잡한 일은 유료·상위 모델로 나눠 쓰게 한다」
- 범위 밖: 파티션 테이블 설계 추천(따로 분석 중)

## 0. 결론

1. **모델은 「주 모델」과 「가벼운 일 모델」 두 칸만 둔다.** 명령마다 모델을 고르게 하지 않는다. 명령이 어느 쪽인지는 앱이 정한다.
   가벼운 일 모델을 비워 두면 지금과 똑같이 모두 주 모델로 간다(옛 설정 그대로 동작).
2. **가벼운 일은 도구를 쓰지 않는 한 번짜리 요청으로 만든다.** 앱이 문맥을 정해진 방식으로 모아 한 번에 보내고, 모델은 글만 쓴다.
   작은 로컬 모델은 도구 호출이 불안정하기 때문이다. 도구 루프(튜닝·벤치마크)는 주 모델만 한다.
3. **가벼운 일도 입력이 크면 저절로 주 모델로 올린다.** 기준은 가벼운 일 모델 프로필의 `MaxInputTokens` 다. 사용자가 고를 일이 없다.
4. **실패했을 때 몰래 다른 모델로 넘기지 않는다.** 보내는 곳이 바뀌면 가림 규칙과 경고 창의 내용도 바뀌기 때문이다. 오류 카드에 「주 모델로 다시 보내기」 단추 하나를 둔다.
5. **대화가 필요한 일은 AI 채팅창, 대화가 필요 없는 일은 그 자리에서 바로 처리한다(§2.1).** 새 결과 창은 어느 쪽도 만들지 않는다.
   - 채팅창: 조사(도구)·여러 번 묻고 답하기·긴 설명. 파티션 추천과 같은 방식(`IAiChatConversation` 대화 주인 + `ChatCardEntry` 기능 카드).
   - 바로 처리: 답이 짧고, 그 화면의 그 자리에서 곧바로 쓰이는 일. 화면 안의 작은 AI 띠에 답을 보이거나 편집기 제안 막대로 넣는다. 띠의 「채팅에서 이어 보기」를 누를 때만 채팅창으로 넘긴다.
6. 1순위 4건, 2순위 2건을 모두 이 두 칸 구조 위에 올린다. 공통 부품(§2)을 먼저 만들면 나머지는 「입구 단추 + 문맥 모으기 + 프롬프트」 정도의 일이다.

## 1. 모델 나눠 쓰기 (공통 기반, P0)

### 1.1 지금 구조

- 설정에는 실행 대상이 하나뿐이다: `AiSettings.Driver`·`ActiveProfileId`·`SystemCliId` + `Model`·`Effort`(`src/Oranda.Core/Settings/AppSettings.cs`).
- `AiActiveProfile.Find` 가 대상을 하나 고르고, `RoutingAiDriver` 가 그 대상으로 보낸다(`src/Oranda.Platform/Ai/RoutingAiDriver.cs`).
- 보내기 직전에 `AiProfileExpectation` 으로 「경고 창에 적힌 곳 = 실제로 보내는 곳」을 확인한다. 로컬 AI 프로필(`AiLlmProfile.IsLocalAi`)이면 값을 가리지 않는다(D-045).

### 1.2 바꿀 것

| 항목 | 내용 |
|---|---|
| 설정 | `AiSettings.Light` 를 더한다: `{ profileId?, systemCliId?, model?, effort? }`. null = 「주 모델과 같음」. 새 섹션이라 스키마 버전은 그대로 둔다. |
| 요청 | `AiRequest` 에 `Tier`(Main·Light, 기본 Main)를 더한다. 명령 명세(`AiCommandSpec`)가 등급을 정한다. |
| 대상 고르기 | `AiActiveProfile.Find(settings, tier)`: Light 이면서 `Light` 가 비어 있지 않을 때만 그 대상을 고른다. 그 밖에는 지금과 같다. |
| 크기 올림 | Light 요청의 추정 토큰이 가벼운 일 모델 `MaxInputTokens` 의 70% 를 넘으면 Main 으로 바꾼다. 채팅창 답에 「입력이 커서 주 모델로 보냈습니다」 한 줄을 남긴다. 한도는 사용자가 따로 정하지 않는다(아래 「한도 정하기」). |
| 한도 정하기 | 새 설정 칸은 두지 않는다. **Claude CLI·Codex**: 앱이 모델별 한도를 안다(입력 칸 없음). **로컬 AI(Ollama·LM Studio)**: 프리셋 기본값을 200,000 이 아닌 8,192 로 두고, 「연결 확인」 때 서버가 알려 주는 실제 문맥 크기로 채운다(응답 칸 이름은 구현 때 확인). 알려 주지 않으면 8,192 를 쓴다. **그 밖의 API 프로필**: 지금 있는 「최대 입력 토큰」 칸(`AiLlmProfile.MaxInputTokens`)을 그대로 쓴다. 까닭: 지금은 프리셋이 이 값을 채우지 않아 로컬 프로필도 200,000(`DefaultMaxInputTokens`)이 되고, 로컬 서버는 넘친 입력을 오류 없이 잘라 버리는 일이 많다. |
| 확인·가림 | `AiProfileExpectation` 과 가림 여부는 **실제로 고른 대상**으로 계산한다. 경고 창에는 그 대상의 이름을 쓴다. 가벼운 일 모델이 로컬 AI 이면 가리지 않고, 주 모델이 유료면 가린다. 둘이 달라도 각자 규칙대로 한다. |
| 표시 | 채팅창의 답 머리에 답한 모델 이름을 작게 적는다(예: `haiku`·`Ollama qwen3:8b`). 지금 채팅창 머리의 `ModelLabel` 은 주 모델을 보이므로, 턴마다 실제로 답한 모델을 따로 적는다. |
| 이어 묻기 | 채팅창 입력칸에서 이어 물으면 같은 모델로 간다(대화 주인의 `FollowUpAsync`). 「더 깊게」 단추는 주 모델로 채팅창에 **새 대화**를 연다. 앞 대화는 넘기지 않는다(지금의 `GeneralTargetChangedText` 규칙과 같다). |
| 기록 | 감사 기록(`IAgentAuditStore`)에 등급과 모델 이름을 남긴다. |

### 1.3 설정 화면

AI 모델 설정 페이지에 줄 하나만 더한다.

```
주 모델         [ Claude Code · opus        ▾ ]  노력 [ high ▾ ]
가벼운 일 모델   [ 주 모델과 같음            ▾ ]
                  주 모델과 같음
                  Claude Code · haiku          ← 유료만 쓸 때 추천
                  Claude Code · sonnet
                  ── 저장된 프로필 ──
                  Ollama · qwen3:8b (로컬)      ← 무료 로컬
                  LM Studio · …
```

- 명령마다 고르는 칸은 두지 않는다. 사용 복잡도를 줄이는 방향을 따른다.
- 가벼운 일 모델의 노력은 `low` 로 고정한다(Claude Code 일 때). 칸을 따로 두지 않는다.
- 가벼운 일 모델의 입력 한도도 칸을 두지 않는다(§1.2 「한도 정하기」). 가벼운 일 대부분은 수천 토큰 안이고, 한도는 펼친 긴 MyBatis SQL·큰 패키지 소스가 잘리지 않게 막는 장치다.
- 기타 CLI(`CustomCli`)는 DB 도구가 없으므로 가벼운 일 모델로는 고를 수 있고, 주 모델로 고르면 지금처럼 도구 없이 동작한다.
- Codex 같은 시스템 CLI 는 라우터가 모델 칸을 비워 보내므로 「모델 이름」은 고를 수 없고 대상만 고른다.

## 2. 공통 부품 (P0)

| 부품 | 하는 일 |
|---|---|
| 문맥 꾸러미 `IAiContextBundle` | 화면마다 「무엇을 보낼지」를 정해진 방식으로 모은다. 허용 수준(`AiAccessLevel`)보다 높은 칸은 꾸러미에 넣지 않는다. 경고 창에 그대로 보여 준다. |
| 일하는 자리 입구 단추 | 화면 도구 막대의 작은 「AI」 나눔 단추. 누르면 문맥을 모아 **AI 채팅창을 앞으로 띄우고** 새 대화를 연다(`AiChatViewModel.StartConversation(title, owner)`). 활성 조건은 `aiConfigured && aiAccessOn` + 화면별 조건이다. 꺼져 있으면 이유를 툴팁에 쓴다. |
| 대화 주인 | 기능마다 `IAiChatConversation` 하나(예: `LockExplainConversation`). 첫 요청·이어 묻기·멈춤을 맡고, 다른 대화가 열리면 채팅창이 놓는다. 파티션 추천의 `PartitionAdviceConversation` 이 본보기다. |
| AI 띠(바로 처리) | 화면 안에 붙는 작은 결과 영역 `AiInlineStrip`. 요청·멈춤·다시·복사·「채팅에서 이어 보기」를 갖는다(§2.1). 편집기에 넣을 글은 제안 막대로 넘긴다. |
| 기능 카드 | 정해진 답 틀을 채팅창 카드(`ChatCardEntry`)로 그린다. 카드 단추(「편집기에 넣기」·「복사」·「더 깊게」)도 카드 안에 둔다. 편집기에 넣을 글은 기존 「제안 막대·덩어리별 수락」으로 넣는다. 새 결과 창은 만들지 않는다. |
| 정해진 답 형식 | 한 번짜리 요청은 답의 틀(제목·표 칸)을 프롬프트로 고정하고, 틀이 깨지면 그대로 글로 보인다. 다시 묻지 않는다. |

### 2.1 채팅창으로 갈지, 바로 처리할지

기준: **그 화면에서 답을 바로 쓰고, 이어 물을 일이 드물면 바로 처리한다.** 도구로 조사하거나, 답을 두고 이야기를 나눌 일이 많으면 채팅창으로 간다.

| 기능 | 처리 | 까닭 |
|---|---|---|
| 3.1 AWR 계획이 바뀐 원인 | 채팅창 | 도구로 여러 번 조사하고, 원인을 두고 이어 묻는 일이 많다 |
| 3.2 락·세션 상황 풀이 | **바로** (모니터 아래 AI 띠) | 두세 줄 풀이와 다음 조치 하나면 된다. 급할 때 창을 옮기면 느리다 |
| 3.2 KILL 확인 창의 의견 | **바로** (확인 창 안 한 줄) | 모달이라 채팅창을 쓸 수 없다. 앞서 받은 풀이가 있으면 그 결론 한 줄만 다시 보인다(새 요청 없음) |
| 3.3 PL/SQL 오류 고치기 | **바로** (편집기 제안 막대) | 결과가 고친 소스 그 자체다. 까닭 한 줄은 막대에 적는다 |
| 3.3 PL/SQL 코드 설명 | 채팅창 | 설명이 길고 이어 묻게 된다 |
| 3.4 MyBatis 펼친 SQL 튜닝 | 채팅창 | 지금 튜닝과 같은 흐름(도구·벤치마크) |
| 3.4 MyBatis 펼친 SQL 설명 | 채팅창 | 3.3 설명과 같다 |
| 4.1 DDL·변경 묶음 실행 전 검토 | **바로** (실행 창 안 검토 띠) | 실행하려는 그 순간에 보는 점검표다. 위험 항목만 짧게 보인다 |
| 4.2 변경 일지 「이 기간 요약」 | **바로** (일지 위 요약 띠) | 짧은 요약 한 단락이면 된다 |
| 4.2 플래시백 「차이 요약」 | **바로** (차이 화면 위 한 단락) | 같다 |
| 4.2 원복 스크립트 「AI 점검」 | **바로** (원복 창 안 점검 띠) | 빠진 것 목록과 「고친 스크립트를 편집기에」 단추면 된다 |
| (기존) SQL 오류 고치기 | **바로** 로 바꿈 (편집기 제안 막대) | 3.3 과 같은 까닭. 지금은 채팅창으로 간다 |
| (기존) SQL 설명·실행 계획 해설 | 채팅창 그대로 | 길고 이어 묻는다 |

바로 처리하는 부품(§2 표의 「AI 띠」)의 규칙:
- 띠 하나 = 요청 하나. 답한 모델 이름을 작게 적는다. 진행 중에는 「멈춤」, 끝나면 「다시」·「복사」·「채팅에서 이어 보기」.
- 「채팅에서 이어 보기」는 보낸 문맥과 받은 답을 그대로 채팅창의 새 대화 첫 턴으로 옮긴다(다시 보내지 않는다). 이어 묻기는 같은 모델로 간다.
- 경고 창(보내는 곳·가림)은 채팅창 쪽과 똑같이 거친다. 바로 처리한다고 확인을 건너뛰지 않는다.
- 바로 처리하는 일은 대부분 가벼운 일(Light)이다. 4.1 실행 전 검토와 원복 점검만 주 모델이다(도구로 의존 객체를 본다).

### 2.2 채팅창 쪽 동작

채팅창이 닫혀 있거나 다른 대화 중이면: 채팅창을 열고 새 대화로 바꾼다. 앞 대화는 「새 대화」를 누른 것과 같이 놓는다(진행 중이면 먼저 멈출지 묻는다).

AI 는 어떤 화면에서도 **실행하지 않는다**(KILL·DDL·DML·컴파일). 제안 글과 스크립트 초안만 만든다. 실행은 지금처럼 사람이 확인 창을 거쳐 한다.

## 3. 1순위 — 구현 대상

각 기능이 채팅창으로 가는지, 그 자리에서 바로 처리하는지는 §2.1 표를 따른다. 「보이는 곳」 줄에 다시 적는다.

### 3.1 SQL 모니터·AWR: 계획이 바뀐 원인 보기

- 자리: `Features/SqlMonitor/AwrHistoryViewModel`·「튜닝 추천」 탭 옆.
- 입구: 같은 sql_id 에 plan_hash_value 가 2개 이상일 때 「AI로 원인 보기」.
- 보이는 곳: 채팅창.
- 등급: **Main**, 도구 씀.
- 새 도구(읽기 전용, 허용 수준 계획 이상):
  - `get_awr_plan_history(sql_id)`: 계획별 사용 기간, 스냅숏마다 실행당 경과 시간·버퍼 읽기·행 수.
  - `get_awr_plan(sql_id, plan_hash_value)`: 그 계획의 줄(DBMS_XPLAN.DISPLAY_AWR 과 같은 내용).
  - 기존 `get_table_stats` 의 `last_analyzed` 와 계획이 바뀐 시점을 맞춰 본다.
- 답 틀: ① 언제 무엇이 바뀌었나 ② 원인 후보(통계 갱신·바인드 엿보기·인덱스 변경·데이터 양) ③ 권하는 조치. SQL Plan Baseline 고정이 맞으면 그 스크립트를 **편집기 제안**으로 준다.
- 주의: 바인드 캡처 값은 「조회+행 값」 수준에서만 보낸다. AWR 을 쓸 수 없는 서버(라이선스·Tibero)는 기존 화면이 지원하는 범위를 따르고, 입구를 끈다.

### 3.2 세션·락 모니터: 상황 풀이

- 자리: `Features/LockMonitor`(차단 사슬), `Features/SessionMonitor`(고른 세션), `BlockerAlert` 알림.
- 입구: 락 모니터 사슬 줄의 「AI 풀이」, 세션 모니터 고른 줄의 「대기 풀이」.
- 보이는 곳: **바로** — 모니터 아래 AI 띠. KILL 확인 창(`LockKillDialog`)에는 앞서 받은 풀이의 결론 한 줄만 다시 보인다(새 요청 없음, 받은 풀이가 없으면 줄을 숨김).
- 등급: **Light**, 도구 안 씀(앱이 사슬을 모아 한 번에 보낸다).
- 꾸러미: 사슬의 세션별 SID·대기 이벤트·대기 시간·잠긴 객체·잠금 모드·모듈·프로그램, 막는 쪽의 현재·직전 SQL(리터럴 가림 규칙 그대로).
- 답 틀: 상황 한 줄 / 원인 추정 / 권하는 행동(기다리기·누구에게 연락·KILL 을 고려할 조건).
- 허용 수준: **계획 이상**. 사용자명·머신 이름을 보낼지는 결정 항목 3.

### 3.3 PL/SQL 편집기: 오류 고치기·설명

- 자리: `Features/PlsqlEditor`, `Features/PlsqlRun`.
- 입구: 지금 SQL 탭에만 있는 「오류 고치기」·「SQL 설명」의 활성 조건(`sqlDocFocus`)을 PL/SQL 문서까지 넓힌다. 설명은 PL/SQL 문서에서 「코드 설명」으로 이름을 바꿔 보인다.
- 보이는 곳: 오류 고치기 = **바로**(편집기 제안 막대, 까닭 한 줄). 코드 설명 = 채팅창.
- 등급: **Light**. 소스가 크면 §1.2 의 규칙대로 Main 으로 올린다.
- 꾸러미: 컴파일 오류 목록(`ALL_ERRORS`), 오류 줄 앞뒤 40줄, 패키지면 spec 전체, 부르는 객체의 정의(메타데이터 수준).
- 결과: 고친 소스는 편집기 제안 막대로 넣는다. 컴파일은 사람이 한다.

### 3.4 MyBatis 작업 공간: 펼친 SQL 튜닝·설명

- 자리: `Features/MyBatisWorkspace`.
- 입구: 지금 `!mybatisDocActive` 로 막힌 AI 명령을 연다. 대상은 **지금 조합으로 펼친 SQL** 이다.
- 보이는 곳: 채팅창(튜닝·설명 모두).
- 등급: 튜닝은 Main(도구 씀), 설명·오류 고치기는 Light.
- 바인드: 파라미터 값은 기존 리터럴 가림 규칙대로 한다.
- 결과: 재작성 제안은 펼친 SQL 을 기준으로 보이고 **XML 에 자동으로 되돌려 넣지 않는다**. 동적 태그(`<if>`·`<foreach>`)에 맞춰 되돌려 넣는 일은 나중에 한다. 인덱스 제안은 그대로 쓸 수 있다.

## 4. 2순위 — 구현 대상

각 기능이 채팅창으로 가는지, 그 자리에서 바로 처리하는지는 §2.1 표를 따른다. 「보이는 곳」 줄에 다시 적는다.

### 4.1 DDL·변경 묶음 실행 전 검토

- 자리: `Features/ChangeBundle` 실행 창, `Features/TableEdit` DDL 미리 보기(파티션 전환 스크립트 포함).
- 입구: 「AI 검토」. 실행 단추를 막지 않는다. 검토는 조언이다.
- 보이는 곳: **바로** — 실행 창 안 검토 띠(위험도 + 점검 항목). 「채팅에서 이어 보기」로 넘길 수 있다.
- 등급: **Main**, 도구 씀(잘못 짚으면 비용이 크다).
- 새 도구(읽기 전용, 메타데이터 수준): `get_dependents(object)`. 무효화될 객체, 참조하는 FK, 트리거, 동의어 수를 준다. 크기는 기존 `get_table_stats` 를 쓴다.
- 답 틀: 위험도(낮음·보통·높음) + 표(잠금 시간·무효화·공간·소요 시간·되돌리기 가능 여부) + 권하는 실행 순서·시간대.
- 앱이 이미 정해진 규칙으로 내는 경고(예: Tibero 지운 열 데이터 경고)는 그대로 둔다. AI 는 그 위에 덧붙인다.

### 4.2 변경 일지·플래시백·원복 요약과 점검

- 자리: `Features/ChangeJournal`, `Features/Flashback`, `Features/Rollback`.
- 입구: 변경 일지의 「이 기간 요약」, 플래시백 버전 차이의 「차이 요약」, 원복 스크립트 창의 「AI 점검」.
- 보이는 곳: 모두 **바로** — 각 화면 위 요약 띠, 원복 창 안 점검 띠(「고친 스크립트를 편집기에」).
- 등급: 요약은 **Light**, 원복 점검은 **Main**.
- 허용 수준: 행 값은 「조회+행 값」일 때만 보낸다. 그보다 낮으면 테이블·열 이름과 건수만 보내고, 카드에 「값 없이 요약했습니다」를 적는다.
- 원복 점검: 일지의 변경과 원복 스크립트를 맞대어 빠진 행, 순서가 틀린 곳(FK), 시퀀스·트리거 부작용을 짚는다. 고친 스크립트는 제안으로만 준다.

## 7. 정할 것

1. **가벼운 일 모델이 실패할 때** — 시안: 자동으로 넘기지 않고 「주 모델로 다시 보내기」 단추 하나. 자동으로 넘기길 원하면, 둘 다 같은 가림 규칙일 때만 넘기는 안이 있다.
2. **크기 올림 기준** — 시안: 가벼운 일 모델 한도의 70%. 한도는 사용자가 정하지 않는다(CLI 는 앱이 알고, 로컬은 「연결 확인」 때 서버에서 읽고 모르면 8,192). 아예 올리지 않고 잘라 보내는 안도 있다.
3. **락·세션 풀이에 사용자명·머신 이름을 보낼지** — 시안: 「계획」 수준이면 가리고(`USER1`·`HOST1` 처럼 자리표시), 「조회」 이상이면 보낸다.
4. **AWR 원인 보기의 라이선스 표시** — Diagnostics Pack 이 필요한 뷰를 쓴다. 기존 AWR 화면의 안내를 그대로 쓸지 정한다.
5. **MyBatis 재작성의 XML 반영** — 시안: 이번에는 하지 않는다.
