# TSK-07-07 Role 구성별 성능 비교 결과서

Role 구성(V0 설정 없음, V1 R1 SQL 개발자, V2 R3 MyBatis 개발자, V3 R4+R5 튜너+DBA, V4 R6 조회 전용)마다 같은 PC·같은 Release 게시본으로
시작 시간, 접속 0·탭 0 유휴 30초 메모리, 스레드·핸들 수, 돈/건너뛴 시작 작업, 상태 칸 수를 쟀다. 판단 기준은 decisions D-003(유휴 전용 메모리 차 15 MB 이상 또는 10 % 이상이면 어셈블리 분리 검토).

**결론(D-003): 분리하지 않음.** V0 와 가장 작은 구성의 유휴 전용 메모리 차는 게시본 기준 3.4 MB(1.7 %), 앱 안 재측정 1.5 MB(0.8 %)로 두 기준 모두 훨씬 아래다. 근거는 6장.

**못 잰 것(참고): 「미커밋 DML 뒤 1분 동안 앱이 연 DB 세션 수」.** 이 PC 의 podman 머신이 꺼져 있고(127.0.0.1:1521 연결 거부) `ORANDA_IT_ADMIN_PASSWORD` 가 환경에 없어 DB 시나리오를 돌리지 못했다. 시나리오(`Oranda.Perf.Ui sessions`)와 실행 스크립트는 만들어 두었고 컴파일·옵션 시험까지 통과했다. 대신 V4 에서 블로커 칸(= 감시기·15초 폴링·모니터 세션의 주인)이 아예 만들어지지 않음을 수치로 보였다(4.2절). 세션 수 자체는 5장의 방법으로 사람이 다시 재야 한다.

## 3. 측정 방법

- 게시본 실행: 구성별 고정 데이터 폴더, 라운드 14회(앞 2회 버림 → 12회), 라운드마다 5구성을 **돌려 가며** 한 번씩(`run-roles.ps1`), 입력 가능 표식 뒤 30초 유휴에서 전용 작업 집합(Windows 「활성 개인 작업 집합」)·커밋·작업 집합 전체·스레드 수·핸들 수를 읽고 프로세스를 끈다. 표식 app-init → composed → settings-loaded → shell-attached → first-render → input-ready 는 앱의 `PerfMarks`. 돈/건너뛴 시작 작업·상태 칸은 앱 Trace 로그(`시작 작업: 돈 N개, 건너뜀 M개`, `상태 칸 건너뜀: 형`)를 이번 실행 몫만 읽어 온다(TSK-07-03 이 남기는 줄).
- 판정 통계는 중앙값, p95 는 nearest-rank(n=12 이므로 사실상 최댓값).
- 앱 안 재측정: 같은 게시본 방식(R2R)으로 `Oranda.Perf.Ui` 를 게시해 구성 5개를 돌려 가며 3라운드(n=3). 기동 3.5초 뒤 30초 유휴 → 전용 메모리 5회(1초 간격)의 중앙값. 이 프로세스는 하네스라 메모리 절댓값은 게시본과 조금 다르다 — 구성끼리의 차이만 본다.

### 4.4 미커밋 DML 뒤 1분 동안 앱이 연 DB 세션 수 — 못 쟀다 (참고)

| 구성 | 기대(코드 읽기) | 측정 |
|---|---|---|
| V0, V1, V1b(`sqlDev,-blockerAlert`: 블로커만 끈 쓰기 가능 구성), V4 | V0·V1 = 작업 세션 1 + 블로커 모니터 세션 1 = 2, V1b·V4 = 1 | **미측정** |

- 이유: podman 머신(`podman-machine-default`)이 꺼져 있어 `127.0.0.1:1521` 연결 거부이고, `ORANDA_IT_ADMIN_PASSWORD` 가 이 세션 환경에 없다. 새 컨테이너를 띄우거나 컨테이너 설정에서 비밀번호를 꺼내 쓰지 않았다(README: 상주 컨테이너, 비밀번호는 사용자가 줌).
- 시나리오(`Oranda.Perf.Ui sessions`): 레인 전용 사용자 `ORA_PF_<hex>` 를 만들고, 앱의 접속 서비스로 접속하고, 앱 실행 컨트롤러로 `insert` 를 실행(자동 커밋 꺼짐)한 뒤, 5초·30초·60초에 그 사용자의 `V$SESSION` 수를 센다. V4 에서는 쓰기 문이 막혀 미커밋 자체가 없다고 보고서에 함께 남긴다(그래서 쓰기가 되면서 블로커만 끈 V1b 를 같이 잰다).
- 사람이 하는 법: 컨테이너를 올리고 `ORANDA_IT_ADMIN_PASSWORD` 를 준 뒤 `pwsh scripts/perf/run-roles.ps1 -SkipPublish -SkipStartup -SkipRolesUi -Out artifacts/perf-roles-rot` (3회 × 4구성, 구성당 약 3분). 결과는 `artifacts/perf-roles-rot/ui-sessions/*.md`.

## 5. 흔들림과 한계

- **구성 순서와 부하**: 1차(구성 순서 고정, V0 가 늘 맨 앞)는 V0 5,018 / V1 4,721 / V2 4,180 / V3 3,935 / V4 4,015 ms 로 앞 구성이 느리게 나오고 CPU 평균도 39.6 % 로 높았다(측정 직전 CPU 평균은 V0 44 %, V1 47 %, V2 41 %, V3 39 %, V4 31 % 로 앞 구성 쪽이 더 바빴다). 1차는 구성과 자리가 같아 둘을 가를 수 없으므로 시작 시간에는 쓰지 않는다. 구성을 돌린 2차에서는 자리별 중앙값이 3,484 / 3,500 / 3,419 / 3,410 / 3,509 ms 로 평평해 자리 효과가 없고, 부하도 평균 20.9 % 로 낮아 이 값을 판정에 쓴다.
- **시작 시간 차**: 2차에서 V4 가 V0 보다 약 550 ms(15 %) 빠르다(3,035 vs 3,582). CPU 30 % 이하인 실행만 모아도 V4 3,031 / V0 3,396 / V1 3,574 / V2 3,540 / V3 3,418 로 같은 방향이다(약 360 ms, 11 %). 줄어드는 구간은 app-init 이후(첫 프레임 -260 ms, shell-attached -200 ms)로 메뉴·상태 칸·도킹을 덜 짓는 몫이다. V1~V3 는 V0 와 ±5 % 안이고 p95 가 3,000 ms 단위로 흔들려 구분하지 못한다. 표본이 12개라 p95 는 한두 번의 튐에 좌우된다.
- **절대 시간**: TSK-11-03 의 2.6 s(같은 PC·부하 적을 때)보다 큰 3.0~3.6 s 다. 2차 중에도 다른 레인이 같은 PC 를 쓴다. 이 결과서는 구성끼리의 비교만 의미가 있고 PRD 7.2 의 1.5 s 판정에는 쓰지 않는다.
- **메모리 튐**: 한 실행의 전용 메모리가 220~650 MB 까지 튄 경우가 1차(라운드 4~5, V1·V3·V4 221~258 MB)와 2차(라운드 3~5, V1 308·V2 653 MB 등)에 있다. 두 회차 모두 라운드 3~5(측정 시작 약 15~20분 뒤)에 몰렸고 구성과는 무관해 보인다. 앱 로그에서 원인을 찾지 못했고 중앙값에 영향이 없어 그대로 둔다. 외부 요인(다른 레인의 부하나 운영체제의 메모리 정리)으로 추정하며 확인하지는 못했다.
- **화면 잠금**: 시작 표식은 첫 프레임을 쓰므로 잠금이 있었다면 값이 튀었을 것이다. 2차 12×5 실행이 모두 정상 범위였다. 렌더 지연 점검(`EnsureDisplayIsLive`)은 이 방식에는 필요 없어 쓰지 않았다.
- 관리 힙은 앱 안 재측정에서만 읽을 수 있다(게시본 바깥에서는 못 읽는다). 하네스 프로세스 값이라 절댓값은 참고.
- 접속 뒤 메모리(탭·접속 열린 상태에서 기능 코드 로딩 차)는 이 Task 범위가 아니라 재지 않았다.

## 6. D-003 판정

| 기준 | 값 |
|---|---|
| V0 − 가장 작은 구성, 게시본 2차(4.1): 201.2 − 197.8 (V4) | **3.4 MB (1.7 %)** |
| V0 − 가장 작은 구성, 게시본 1차(고정 순서): 198.0 − 195.8 (V1) | 2.2 MB (1.1 %) |
| V0 − 가장 작은 구성, 앱 안 재측정(4.2): 195.3 − 193.8 (V1) | 1.5 MB (0.8 %) |
| 기준 | 15 MB 이상 또는 10 % 이상이면 분리 검토 |

**판정: 분리하지 않음.** 세 번의 측정 모두 기준의 1/4 이하이고, 같은 방향(큰 구성이 작은 구성보다 0~3 MB 큼)이어도 측정 흔들림(±3 MB) 안이다. 관리 힙(65~69 MB)과 로드된 어셈블리 수(75개, 구성 무관)도 구성에 따라 달라지지 않는다 — 기능을 꺼도 어셈블리·ViewModel·처리기가 지연 생성이라 이미 접속 전에는 메모리를 안 잡고 있다(D-003 근거의 추정, 처리기·ViewModel 이 지연 생성이라 메뉴에서 빼는 것만으로 메모리 이득이 작다는 것과 일치). 어셈블리 분리(Oranda.App.MyBatis·Tuning·Dba)의 예상 이득은 접속 0·탭 0 유휴에서 3 MB 이하라 일이 큰 데 비해 얻는 것이 없다.

그 대신 이 회차에서 보인 이득은 다음이다.
- 시작 초기화: 시작 작업 14 → 8~13개, 상태 칸 10 → 7~10개, V4 는 블로커 감시기(타이머·모니터 세션)를 아예 만들지 않는다.
- 시작 시간: V4 만 약 11~15 % 짧다(메뉴·도킹 덜 짓는 몫). 나머지는 구분되지 않는다.

새 WP 로 올릴 후보는 없다. 다시 판단할 계기: 접속 뒤(탭·결과 열림) 기능 코드 로딩 메모리나 DB 세션 수 측정에서 구성 간 큰 차가 나올 때.
