# TSK-04-01 MyBatis 작업 공간 흐름 시험 결과서

매퍼 열기부터 매퍼 폴더 열기까지 한 줄로 잇는 흐름 시험(UI 위주, DB 는 쓰지 않음)과 PRD 6 성능 수치를 win144 에서 다시 쟀다.
사용자가 준 실제 사내 매퍼(쿼리 153개, 저장소 밖)와 시안 표본 매퍼(`EmpMapper`) 둘로 돌렸다.

사용자 매퍼 시험 = `ORANDA_USER_MAPPER=<경로>` 설정 뒤 실행(없으면 해당 시험은 건너뜀).

## 범위와 규칙

- DB 실행(시나리오 값으로 실행, 실행 계획 EXPLAIN, 11g·19c 비교)은 하지 않았다. 조합 검사는 「구문 분석만」 방식이다. 이 항목은 아래 「사용자 확인」 으로 넘긴다.
- 사내 매퍼는 절대 경로로 **읽기만** 했다. 시험은 임시 폴더에 복사본을 만들어 고치고 저장하며, 시험 뒤 지운다. 저장소·tests 에 복사하지 않았고, 이 결과서에도 쿼리 본문·테이블·변수 이름을 적지 않았다(개수·길이·시간만).
- 사용자 매퍼가 없는 PC 에서는 사용자 매퍼 시험이 아무것도 하지 않고 통과한다(공개 저장소 규칙). 이 PC 에서는 파일이 있어 모두 실제로 돌았다.
- 앱 조립(`ShellHarness`)이 만든 실제 훅·계산 허브·시나리오 저장소·편집기 공장·폴더 서비스를 그대로 썼다. 바꾼 것은 저장 확인 창(응답기)과 알림 대화 상자뿐이다.

### 읽는 법

- 3b 는 「조합 256개 3 s」 의 환산이다. 사용자 매퍼에는 조건이 8개 이상이라 조합이 256개 나오는 문장이 없어(조건 1~4개이거나, 130개 넘어 「줄이기」로 80~138개) 실제 256개 실행은 합성 시험(3a)이 맡고, 사용자 매퍼는 조합 하나의 분석 시간을 재 256 을 곱했다.
- 조합 하나의 분석은 문장 캐시에 걸리지 않게 글자만 다른 변형 20개를 분석해 평균했다(토큰은 같다). 즉 ANTLR 예측 캐시가 데워진 뒤의 값이다. 같은 모양을 처음 보는 첫 분석은 3d 로 따로 적었다.
- Debug 와 Release 가 크게 다르지 않다. 파서가 Release 에서도 같은 비용이라는 뜻이고, 시간은 코드가 아니라 ANTLR 예측 캐시 만들기에 쓰인다(아래 결함 TSK-03-11).
- 모든 수치는 CPU 24~97 % 부하 속 값이라 무부하 값은 이보다 낮을 것이다. 맥 Debug 수치(TSK-04-02: 막힘 53 ms, 훑기 248 ms)와 훑기 시간이 크게 다른 까닭은 Windows 의 파일 열기 비용(실시간 검사 포함)과 이 PC 의 부하로 보이며, 실제 원인 구분은 결함 TSK-03-13 에 맡긴다.

## 성능 원인 조사와 고침

| 항목 | 조사 | 결과 |
|---|---|---|
