## 측정 환경

- PC: MacBook, Apple M5, 메모리 16 GB, macOS 26.6.2, .NET SDK 10.0.402
- 빌드 구성: Debug (`-c Debug`). Release 는 실행 중인 앱 파일을 건드릴 수 있어 재지 않았다
- 측정 시각: 2026-10-23 15:07(+09:00), 측정 창 안, 다른 레인 없음. 시작 전 load 1분 값 2.55
- 명령: `dotnet test tests/Oranda.App.Tests -c Debug --no-build --filter "Category=Perf&FullyQualifiedName~MyBatis"` 1회(시험 6개, 6/6 통과, 전체 실행 시간 2.3 s: 시험 클래스가 병렬로 돈다)
- 기준 커밋: 5b1e996(dev-jji-mac 3bb21b2 포함)
- 리뷰 뒤 시험 코드를 고쳐(3,000줄 문장을 2,999줄에서 3,005줄로, 막힘 측정에 try/finally) 같은 명령을 1회 더 돌렸다(15:11, 측정 창 뒤, load1 10 안팎로 다른 빌드와 일부 겹침, 6/6 통과). 1c 수치는 이 회차 값이다: 열기 14 ms. 나머지는 1a 35 ms, 1b 142 ms, 2a 평균 0.15 ms, 2b 평균 4.92 ms, 4 막힘 50 ms(훑기 전체 242 ms)
- 이 맥 Debug 수치 = 상한값으로 읽는다. PRD 의 수치는 시험 PC 기준이며, win144 수치는 TSK-04-01 결과서에 함께 적는다
- 아래 표의 PC·빌드 구성은 모두 위 환경(M5 맥·Debug)이다

## 시험 설명

- 1c: 문장 하나(select)가 3,005줄(`<where>` 안 `<if>` 를 세 줄씩)인 매퍼에 작은 문장 하나를 더했다. 「문장」 창을 화면에 둔 채 열고 첫 레이아웃까지 쟀다. 측정 범위는 목록까지이고 문장 탭 편집기(강조·흐림 계산)는 포함하지 않는다(PRD 문구 「문장 목록이 보일 때까지」)
- 2: 디바운스(300 ms)가 끝난 뒤 계산 한 번(`Flush`)과 바인드 행·펼친 SQL 갱신까지 잰다. 디바운스 시간 자체는 상한에 넣지 않았다
- 4: 폴더 20개 × 매퍼 100개(요소 4개씩)를 만들고, 작은 폴더로 먼저 데운 뒤 `MapperFolderService.OpenAsync` 와 폴더 트리 화면을 함께 잰다. 다른 스레드가 5 ms 마다 UI 스레드에 일을 던져, 던진 때부터 실행될 때까지의 지연 최댓값을 막힘으로 삼는다

## 관찰·남긴 일

- 폴더 훑기 막힘은 부하에 민감하다. 다른 레인 빌드와 겹친 단독 실행에서는 301 ms 가 나와 같은 시험이 실패했고(load 17.9), 부하가 낮은 회차에서는 53~59 ms 였다. 상한 100 ms 는 이 맥에서 여유가 크지 않다
- 막힘의 원인으로 의심되는 곳은 훑기가 끝난 뒤 `MapperFolderTreeViewModel.Rebuild`(03-07 소유)가 UI 스레드에서 트리 전체(노드 약 10,000개)를 다시 짓는 부분이다. `Rebuild` 시간은 따로 재지 않은 추정이다. 가상화·점진 생성은 하지 않았다. win144 에서 상한을 넘으면 defect 후보로 올린다
- 같은 프로세스의 다른 시험 클래스가 병렬로 도는 중에도 이 시험은 UI 스레드를 공유한다. 막힘이 크게 나오면 `--filter FullyQualifiedName~Scanning_a_folder_of_2000` 으로 단독 실행해 다시 확인한다
- 조합 256개 시험은 경과 시간을 출력하지 않는다. 필요하면 시험에 출력을 더한다(이 Task 에서는 하지 않았다)
