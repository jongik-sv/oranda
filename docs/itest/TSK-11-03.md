### 1.2 측정 방식 요약

- 시작·유휴 메모리: 게시본 `Oranda.App.exe` 를 `ORANDA_PERF` 표식으로 12회(앞 2회 버림) 띄움. 메모리는 Windows **전용 작업 집합**(작업 관리자의 「활성 개인 작업 집합」)을 판정 값으로, 커밋(전용 바이트)은 참고로 적는다. macOS 는 `footprint`(phys_footprint).
- 창 시나리오: 진짜 앱(Oranda.App)을 진짜 창으로 띄우고 앱의 명령·서비스로 동작(접속, 탭 열기, 실행, 취소, 자동완성)한다. 키 입력은 이벤트 주입이고 렌더 스레드가 그릴 때까지 잰다.
- 통계: 항목마다 표본 n, 중앙값, p95(가장 가까운 순위), 최대. PRD 가 정한 통계(시작·메모리는 중앙값, 지연은 p95)로 판정한다.

### 1.3 측정 한계

1. **화면 잠금 (이 결과서의 가장 큰 한계).** 측정 도중(약 09:14, 사용자 입력 없이 15분 뒤) 콘솔 세션이 잠겨 창이 가려진 것으로 처리되었다. 이후 렌더 배치 하나가 250~700 ms(잠금 전 약 30 ms) 걸려 키 입력 「반영」·그리드 프레임 간격 같은 렌더 의존 값이 쓸 수 없게 됐다. 도구는 이제 시작할 때 이를 감지해 중단한다(`화면이 잠겼거나 창이 가려져…`). 잠금 뒤 측정으로 유효한 것: 시작 시간(표식이 렌더와 무관하게 거의 같은 분포), 포맷·문법 검사·취소(렌더와 무관). 잠금 전 1회차: 키 입력·자동완성·첫 행·그리드·접속 메모리(이 값들은 최종 커밋이 아니고 일부는 하네스 JIT 빌드/단일 회차다).
   - 다시 재는 법: 화면 잠금 시간을 늘리거나 해제한 PC 에서 `pwsh scripts/perf/run-windows.ps1` (README 참고). 맥북에서는 `scripts/perf/run-macos.sh`.
2. 접속 3개는 앱이 작업 접속을 하나만 두기 때문에(`IConnectionService.ActiveSession`) 활성 1 + 세션 관리자로 연 작업 세션 2로 만들었다.
3. 「최초 실행」은 OS 파일 캐시를 못 비운다. 대신 게시 폴더를 새 임시 폴더에 복사해 띄웠다(새 파일 → 백신 검사).
4. 입력은 실제 키보드가 아니라 이벤트 주입이다. 모니터 스캔아웃은 빠진다.

### 2.1 판정 근거 메모

- 항목 3: PRD 의 「전용 메모리」 정의가 없다. Windows 전용 작업 집합을 판정 값으로 삼았다(작업 관리자 표시와 같음, macOS phys_footprint 와 가장 가깝다). 커밋 메모리로 보면 204~236 MB 로 더 크다. 어느 쪽이어도 초과다. 정의는 PRD 에 못 박아야 한다(DEF-02).
- 항목 7: PRD 문구 「입력 멈춘 뒤 300 ms」 가 모호하다. 디바운스(TRD 4.5, 300 ms)가 한도를 이미 다 쓴다. 디바운스 뒤 값으로 보아도 초과다(DEF-04).
- 항목 10 「행당 200 bytes」: 데이터 포함인지 불분명하다(DEF-06).
- 항목 5: 처리 시간은 D-007 정의(렌더 틱 대기 제외)다. 틱 대기를 넣은 반영 시간 p95 는 55~59 ms 로 16 ms 를 넘는다. PRD 문구가 어느 쪽인지 확정이 필요하다.

정리하면 **총 2.6 s 중 약 1.65 s 는 `Main` 앞뒤의 프로세스·Avalonia 플랫폼 초기화(셸 코드가 아님)** 이고, 이 앱 자신의 코드(조립 + 창 생성 + 셸 부착 + 시작 작업)는 합쳐 약 0.4 s, 첫 프레임 레이아웃이 0.5~0.6 s 다. `spikes/TSK-01-04` 가 같은 PC 에서 빈 Avalonia 창이 composite R2R 에서 1,830 ms 라고 이미 쟀다(Main 앞 약 500 ms, 플랫폼 초기화 약 1.0 s, 첫 프레임 72 ms). 현재 앱은 그 위에 약 0.6 s(첫 프레임 +0.5 s, 창·셸 +0.1 s)를 더한다.

### 4.2 composite R2R 은 실제로 쓰였나

- 게시 폴더에 `Oranda.App.r2r.dll`(109 MB, composite 이미지)이 있다.
- `DOTNET_ReadyToRun=0` 으로 R2R 코드를 쓰지 않게 하면 입력 가능 중앙값이 2.5 s → **4.4 s**(n=6)로 +1.9 s 늘어난다. R2R 은 효과를 내고 있다. `DOTNET_TieredPGO=0`(2.7 s), `DOTNET_TieredCompilation=0`(2.5 s)은 차이가 없다.
- 그래도 시작·유휴 9 s 동안 **JIT 된 메서드가 3,364개**다(EventPipe `MethodJittingStarted`). 상위: System.Collections 363, Avalonia.Media 255, Avalonia.Controls 216, Avalonia.PropertyStore 214, Avalonia.Rendering 169, System.Linq 152, dynamicClass 110(컴파일된 XAML·식 트리). 값 형식 제네릭 인스턴스와 람다라 R2R 이 미리 만들지 못한 것이다. R2R 을 끈 경우의 +1.9 s 로 어림하면 이 3.4천 개의 JIT 비용은 0.2~0.4 s 이다.

### 4.3 Defender 영향

- 관리자 권한이 없어 게시 폴더 제외 전후 비교는 못 했다(추정).
- 간접 증거: 방금 게시(또는 새로 복사)한 파일의 첫 실행이 매우 느리다. 게시 직후 첫 4회는 30 s 제한 안에 끝나지 못했고(AppBuilder 8.3 s, 창 생성 28 s), 5번째부터 2.5 s 대로 돌아왔다. 새 복사본에서 시작한 5회는 9~33 s(중앙값 11.3 s)다. 검사가 끝난 뒤(웜)는 영향이 작다고 본다. 따라서 **최초 실행 4 s 목표**와 **설치 직후 첫 실행**은 백신 검사가 지배하고, 앱이 줄일 수 있는 것은 파일 수·크기뿐이다(262개, 300 MB. PDB 100 MB 포함 → DEF-07).
- `spikes/TSK-01-04/RESULT.md` 는 이 PC 에 사내 백신(AhnLab V3)이 돈다고 적었다. 이번 측정 때 V3 서비스 프로세스는 확인하지 못했다.

### 4.4 macOS 391 ms 와 약 7배 차이

macOS 값은 M5(10코어, 단일 스레드 성능이 이 i5-1135G7 의 2배 안팎), 빈 데이터 폴더, `.app` 이 아닌 실행 파일 직접 실행, 일반 R2R(composite 아님)이다. 같은 PC 의 spike 로 설명되는 Windows 고유 비용:

1. 프로세스의 첫 STA/첫 창 생성 약 430 ms: hello 콘솔에서도 같은 값(spikes/TSK-01-04 ①). 이 PC 고유 비용으로 추정, 다른 PC 에서 확인 필요(사람 자원).
2. Avalonia Win32 플랫폼 초기화 약 1.0 s: 메시지 창, ANGLE/D3D11, 렌더러. macOS 는 Metal/AppKit 이라 같은 단계가 수십 ms.
3. 첫 프레임 0.5~0.6 s: Dock 레이아웃과 합성기 첫 배치. 맥에서는 첫 렌더 전체가 293 ms.
4. 백신 실시간 검사: 새 파일이 아니어도 DLL 적재마다 검사 훅이 끼어들 수 있다(추정).
5. 게시 파일 262개·300 MB(맥 160 MB). 적재할 어셈블리·네이티브 DLL 이 더 많다.
이 중 앱이 줄일 수 있는 것은 3·5(그리고 JIT 3.4천 개), 줄이기 어려운 것은 1·2·4(환경·프레임워크)다. 1.5 s 목표가 이 PC 에서 도달 가능한지부터 판단해야 한다(DEF-01).

### 4.5 유휴 메모리 159~194 MB (목표 150 MB)

- 접속·탭 없음 159~173 MB(전용 작업 집합), 커밋 204~218 MB. 관리 힙 42 MB 뿐이라 나머지는 네이티브: 런타임·JIT 코드·Skia/ANGLE(libSkiaSharp 11 MB, av_libglesv2 5 MB)·글리프/텍스트 캐시·R2R 이미지의 전용 페이지.
- 접속하면 +20 MB(ODP.NET 드라이버·세션·딕셔너리 캐시), 탭을 열면 +수 MB. 맥은 접속·탭 없이 131.6 MB 이므로 같은 구조에서 Windows 가 약 30~40 MB 많다.
- 접속 3 + 10만 행 ×3 은 270 MB 로 여유가 있다(결과는 임시 파일로 내려가는 페이지 캐시 200 MB 상한).

### 4.6 문법 검사

디바운스 300 ms 를 빼고도 분석+반영이 중앙값 422~497 ms 다(1만 줄 문서의 맨 끝 줄 하나만 고쳐도). 첫 전체 분석이 1.6~2.1 s 이므로 증분 분석이 기대만큼 문장 단위로 줄지 않거나 반영 단계(밑줄 갱신·`Current` 계산)가 문서 전체를 훑을 수 있다. 정확한 지점은 프로파일이 필요하다(DEF-04).

### 4.7 실행 취소

sleep 중에는 취소 명령 뒤에도 서버 호출이 끝날 때까지 기다린다(59.3 s, 10회 모두). 취소 신호가 서버 대기를 깨우지 못하거나 아예 호출하지 않는다. CPU 루프는 1.7 s 로 서버가 중단을 처리하는 데 시간이 걸리거나 정리(롤백)가 길다. 어느 쪽인지는 엔진(`OracleExecutionService`)의 취소 경로를 따라가야 한다(DEF-05).

### 4.8 설치 파일 크기

`vpk pack` 이 앱에서 Velopack 호출을 찾지 못해 중단된다. 앱 소스에 Velopack 참조가 없다(자동 업데이트 코드가 이 커밋에는 없음). 크기는 게시 폴더 압축으로 추정했다: PDB 두 개(libSkiaSharp 80 MB, libHarfBuzzSharp 20 MB)만 빼면 106 → 79 MB 로 내려간다. composite R2R(+약 30 MB)는 시작 시간과의 맞바꿈이다(DEF-07).
