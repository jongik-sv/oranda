## 1. 라이선스 트레이스 0건 확인 방법

서버 쪽에서 직접 센다. 앱이 보낸 SQL 을 기록한 것(앱 쪽 기록)에 기대지 않는다.

| 단계 | 방법 |
|---|---|
| 감시 설정 | 시험마다 **통합 감사 정책**(Unified Audit)을 만든다. 대상 = 팩 필요 객체: `V$/GV$ ACTIVE_SESSION_HISTORY·ASH_INFO·SQL_MONITOR·SQL_PLAN_MONITOR·SQL_MONITOR_SESSTAT·SQL_MONITOR_STATNAME` 뷰, `DBA_HIST_*`(169개), `DBA_SQLTUNE_*` 뷰의 SELECT 와 `DBMS_SQLTUNE`·`DBMS_SQL_MONITOR`·`DBMS_WORKLOAD_REPOSITORY` 패키지의 EXECUTE. 목록은 `dba_objects` 에서 시험 때마다 뽑는다 |
| 세션 가려내기 | 이 시험이 연 세션만 본다: 일반 연결 = `USERENV.UNIFIED_AUDIT_SESSIONID`, Oranda 세션 = 연결 때 앱이 붙이는 `client_identifier`(`oranda:...`). 같은 컨테이너를 쓰는 다른 시험·사람의 조회는 세지 않는다 |
| 판정 | `unified_audit_trail` 에서 위 세션의 행이 **0건**이어야 한다. 정책이 켜져 있는지(`audit_unified_enabled_policies`)도 같이 단정한다 |
| 대조군 (S7) | 같은 감사로 (a) 일부러 `v$active_session_history`·`dba_hist_snapshot` 을 조회한 연결이 잡히는지, (b) 팩 `Diagnostics+Tuning` 을 선언한 Oranda 세션의 SQL 모니터 보고서 호출이 `DBMS_SQLTUNE` 로 잡히는지 확인했다. 둘 다 1건 이상 잡혔다 → 감사 방법이 실제로 동작하고 `client_identifier` 로 Oranda 세션을 가려내는 것도 동작한다 |
| 정적 검사 | 카탈로그 모든 `.sql` 에 `license:` 머리가 있고, 팩 객체를 쓰는 쿼리는 모두 `license` 가 `none` 이 아니다(현재 `plan/monitor_report.sql` 하나, tuning). `src` 전체 grep 으로도 팩 객체 이름은 그 파일 한 곳뿐이었다 |

결과: 시나리오 S1~S6 의 모든 흐름(세션 목록·블로킹 트리·상세·Kill·Top SQL·SQL 전문·바인드·계획·예상 계획·실패 경로) 동안 **팩 객체 감사 행 0건**. S7 에서 선언 없이(없음·Diagnostics 만) Tuning 태그 호출은 서버에 가기 전에 `UnauthorizedAccessException` 으로 막혔고 감사 0건.

한계(정직하게): 감사는 사용자가 보낸 문장이 팩 객체를 직접 참조할 때 기록한다. 서버 내부 뷰 정의 안의 참조는 잡지 못한다. 또 이번 범위는 서비스 계층 흐름이며, "전체 화면 1시간 순회"는 아래 「미실행」.
