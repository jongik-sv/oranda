# 문법 검사 반영 macOS 전후 측정 (TSK-04-09, DEF-04) — 2026-10-20

`docs/itest/TSK-11-03.md` DEF-04(1만 줄 문서 반영 중앙값 422~497 ms, 목표 300 ms)를 고치기 전후를 맥북에서 번갈아 잰 기록이다. 판정 값(Windows `Perf.Ui diagnostics`)은 개발 PC 가 다시 잰다.

## 원인

L2 분석 캐시(문장 원문 → 결과)가 4,096개에 닿으면 분석 도중 통째로 비워졌다. 측정 문서(`SampleSql.EditorDocument(10000)`)는 문장이 7,500개라 분석마다 캐시가 비워지고, 끝에서 문장 하나를 고쳐도 **7,500문장을 모두 다시 파싱**했다(아래 「편집당 파싱 문장 수」). 반영 단계(밑줄 갱신)는 원인이 아니다.

고친 내용(`4467728`): 캐시 상한 16,384, 분석이 끝난 뒤에만 오래 안 쓴 문장부터 버리고 이번·직전 분석이 쓴 문장은 남긴다. 편집하면 바뀐 문장만 파싱하고 나머지는 결과를 새 위치로 옮겨 쓴다. L1 문장 분리는 그대로 문서 전체를 훑는다(1만 줄 약 8 ms, 아래).

디바운스(`4b3a0a5`): 값(300 ms)은 그대로다. 타이머가 75 ms 마다 확인하던 방식이라 분석이 마지막 키 뒤 300~375 ms 에 시작하던 것을, 마지막 키 뒤 약 300 ms(헤드리스 실측 300.2 ms)에 시작하게 했다. 실제 OS 타이머는 해상도만큼(Windows 약 15.6 ms) 늦을 수 있다. 값을 바꾸지 않았어도 이 변경만으로 「마지막 키 → 반영」 은 평균 약 37 ms 줄어든다.

## 두 해석별 정리 (결정: 마지막 키 기준, D-020)

PRD 7.2 「문법 검사 반영 (1만 줄 파일, 입력 멈춘 뒤) 300 ms 이하」:

| 해석 | 판정에 쓰는 값 | 고치기 전 (Windows / macOS 헤드리스) | 고친 뒤 (macOS 헤드리스) |
|---|---|---|---|
| 디바운스 뒤 300 ms | 디바운스 뒤 → 반영 p95 | 중앙값 422~497, p95 478~621 / 중앙값 240.5, p95 1,098.7 | 중앙값 15.3, p95 56.2 → 충족 예상 |
| 마지막 키 뒤 300 ms (디바운스 300 유지) | 마지막 키 → 반영 p95 | 중앙값 789~946 / 중앙값 582.3, p95 1,441.4 | 중앙값 315.9, p95 384.0 → **초과** (디바운스만으로 300) |
| 마지막 키 뒤 300 ms (디바운스 100, 참고) | 마지막 키 → 반영 p95 | - | 중앙값 117.8, p95 139.6 → 충족 예상 |

「마지막 키 뒤」 로 읽으면 디바운스 300 ms 는 분석이 0 ms 여도 한도를 넘는다. 그 해석이면 `EditorDiagnostics.Debounce` 를 100 ms 안팎으로 줄여야 한다(값은 그 한 곳에서만 정한다). 디바운스를 줄이면 입력 중 분석이 더 자주 시작·취소되지만 고친 뒤 분석 한 번이 수십 ms 라 부담은 작다.

## 디바운스 100 ms 적용 뒤 재측정 (D-020, 2026-10-20)

결정 D-020 으로 PRD 「입력 멈춘 뒤 300 ms」 를 마지막 키 기준으로 확정하고 `EditorDiagnostics.Debounce` 를 300 → 100 ms 로 줄였다. macOS 헤드리스(`DiagnosticsLatencyTests`, 1만 줄, n=15, 같은 PC 의 다른 작업이 도는 상태):

| 값 | 전 (디바운스 300 ms, 고친 뒤 캐시) | 후 (디바운스 100 ms) |
|---|---|---|
| 마지막 키 → 반영 | 중앙값 315.9, p95 384.0 ms | 중앙값 122.6, p95 227.5 ms |
| 디바운스 뒤 → 반영 | 중앙값 15.3, p95 56.2 ms | 중앙값 56.7, p95 159.2 ms |
| 마지막 키 → 분석 시작 | 300.2 ms | 106.1 ms |
| 타이핑 중 UI 스레드 최장 정지(1만 줄, 30 ms 간격 60회) | 측정 안 함 | 13.7 ms (시험 한도 100 ms) |

- 마지막 키 기준 p95 가 한도 300 ms 안으로 들어왔다. 「디바운스 뒤 → 반영」 숫자가 전보다 큰 것은 측정 때 PC 부하 차이로 보이며(분석 자체는 바꾸지 않았다) 같은 조건 반복 측정은 하지 않았다.
- 새 시험 `Typing_in_a_10k_line_document_never_blocks_the_ui_thread_for_long`(`Category=Perf`)이 UI 스레드가 한 번에 묶이는 최장 시간을 100 ms 미만으로 단정한다.
- Windows `Perf.Ui diagnostics` 재측정이 남았으므로 TSK-04-09 는 `[ ]` 로 둔다.

## 시험

- `dotnet build Oranda.sln -c Release`: 경고 0, 오류 0 (필터 없는 출력으로 확인).
- `dotnet test tests/Oranda.Language.Tests -c Release` 372 통과, `tests/Oranda.App.Tests` 1,056 통과, `tests/Oranda.Architecture.Tests` 11 통과.
- 새 Language 시험(`IncrementalAnalysisTests`): 편집 14가지(앞·중간·끝, 문장 추가·삭제, 세미콜론 삭제로 두 문장 합치기, PL/SQL 블록 안 편집, 작은따옴표 열기, 문서 전체 바꾸기 등)마다 앞서 분석한 서비스의 결과가 처음 보는 서비스의 전체 분석 결과와 같은지 기본 캐시·작은 캐시(8) 두 가지로 단정한다. 블록 주석을 열었다 닫는 편집, 연속 입력, 캐시 상한 유지, 1만 줄 문서의 편집당 파싱 문장 수도 단정한다. 고치기 전 캐시로 돌리면 3개가 실패한다.
- 새 App 시험(`DiagnosticsLatencyTests`): 디바운스보다 짧은 간격의 입력 묶음에 분석이 한 번이고, 마지막 키에서 디바운스가 지나기 전에는 시작하지 않는다. 1만 줄 측정은 `Category=Perf` 라 기본 실행에서 빠진다.

## 한계

- 부하가 큰 기기에서 쟀다. 값의 방향(A 대비 B 가 10배 이상 빠름, 편집당 파싱 7,500 → 0~1문장)은 모든 회차에서 같다.
- 헤드리스 창이라 진짜 렌더링·화면 반영 시간은 들어 있지 않다. 판정은 Windows `scripts/perf/run-windows.ps1`(Perf.Ui diagnostics)로 다시 잰다.
- L1 문장 분리는 여전히 문서 전체를 훑는다(1만 줄 약 8 ms). 바뀐 줄 근처만 다시 나누는 증분 분리는 남은 선택지다.
- 큰 문서 탭 3개 이상을 번갈아 고치면 캐시 상한(16,384문장)을 넘어 오래 안 쓴 탭의 문장이 버려지고, 그 탭을 다시 고칠 때 한 번 전체를 파싱한다.
