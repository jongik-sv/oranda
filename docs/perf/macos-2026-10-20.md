### 행당 200 bytes 해석

스파이크의 페이지 캐시는 50열 혼합 결과에서 행당 약 2.0 KB(셀당 약 43 B)다. 데이터 자체가 200 B 를 넘으므로, PRD 의 「행당 200 bytes」 가 **데이터를 뺀 그리드 자체의 행당 부담**을 뜻하는지 확인이 필요하다. Windows 스파이크(TSK-01-06 RESULT)는 행당 약 1.0 KB 로 적었다. 같은 코드인데 macOS 값이 약 2배인 이유는 확인하지 않았다.

시작 시간 주의: 실행마다 빈 데이터 폴더를 써서 레이아웃 복원이 없었고, `.app` 이 아니라 실행 파일을 직접 띄웠다(LaunchServices 를 거치지 않음). 두 가지 모두 값을 조금 낙관적으로 만든다. 목표 대비 약 4배 여유가 있어 판정은 유지한다.

## 측정을 막은 결함

화면 결함 1~3 은 `cd14db1` Debug 빌드 화면에서 봤다. `9dea471` 에서는 결함 1 의 원인 코드(구독자 0건)만 grep 으로 다시 확인했다.

1. **SQL 편집기가 실제 앱에서 열리지 않는다.** `oranda.file.newSqlEditor` → `SqlEditorHost.NewDocument()` 는 호스트의 `Tabs` 에만 탭을 넣는다. 셸의 `DockWorkspace.OpenDocument` 로 붙이는 코드가 없다(`SqlEditorHost.TabOpened` 구독자 0건). 메뉴, ⌘+N, 명령 팔레트 모두 「No documents open」 그대로였다.
2. 상태줄에 `Not Found: Oranda.App.Features.SqlEditor.EditorStatusView` 가 나온다.
3. 메뉴가 명령 ID 로 표시된다(`file new sql editor`, `conn manage`). DBMS 출력 패널에 `oranda.panel.output` 이 그대로 보인다.

## dev-jji-win144 CI 실패 (run 39276301319, `9dea471`)

- windows-x64: `StatementSplitterTests.Incremental_lex_of_10k_lines_meets_budget` 실패. 메시지 `propagate 21.0232 ms`(한도 16 ms). 기본 시험 안의 성능 단정 시험이 CI 부하에서 깨진 것이다(idea.md 할 일 1).
- macos-arm64: `ShellHeadlessTests.Menus_are_built_from_the_registry_with_keymap_shortcuts` 실패. 메시지 `Expected: Ctrl+Shift+P / Actual: Shift+Cmd+P`. 시험이 Windows 표기(Ctrl)를 기대하는데 macOS 는 ⌘ 로 표시한다.
- macos-arm64: `ShellHeadlessTests.Command_palette_opens_with_the_keyboard_shortcut_and_runs_a_command` 실패. 메시지 `System.TimeoutException : 조건이 시간 안에 참이 되지 않았다.` 같은 원인(시험이 Ctrl 조합을 보내는데 macOS 키맵은 ⌘)으로 추정한다. 시험 코드로는 확인하지 않았다.

## 측정하며 알게 된 것

- 이 측정 세션의 임시 폴더에서는 모든 실행 파일이 시작 즉시 SIGKILL(137)로 죽었다. 앱 결함이 아니다(`/bin/echo` 복사본도 같다). 게시본은 리포 안 `bin/` 아래에서 실행했다.
- `Process.PrivateMemorySize64` 는 macOS 에서 0 이다. `tests/Oranda.Perf` 의 메모리 칸은 macOS 에서 쓸 수 없으므로 `footprint`(phys_footprint)로 따로 쟀다.
- 그리드 스파이크의 `--render angle` 은 Windows 전용 옵션이라 macOS 에서는 무시되고 기본 GPU 경로로 그린다.
